# 技能创建器

一个用来创建新技能、并反复把它们打磨得更好的技能。

需要先说明本技能的前提：**它不绑定任何特定厂商、IDE 或 CLI**。凡是能运行 Python 且能非交互调用一个 agent CLI 的环境都能用，包括 Claude Code、Codex、Gemini CLI、Cursor、OpenCode、Finch 以及任何自己写的 agent。脚本通过 `scripts/agent_cli.py` 这一层适配器选择 agent，所以换成别的工具不需要改技能内容。以 Claude 为主要工具的用户会在下面看到对应的补充说明，但那些都只是"某个工具的特殊情况"，不是主流程。

从高处看，做一个技能的过程是这样的：

- 想清楚要这个技能做什么，大致怎么实现
- 写一版草案
- 造几个测试用例，让装了技能的 agent 去跑
- 陪用户一起评估结果，既有定性也有定量
  - 跑的同时，如果还没有定量断言就草拟一些（已有的可以直接用，或按需要改）。然后向用户解释这些断言在检查什么
  - 用 `eval-viewer/generate_review.py` 把结果展示给用户看，同时让用户看到定量指标
- 根据用户对结果的评价重写技能，顺带修掉定量数据暴露出来的明显问题
- 反复，直到满意
- 扩大测试集，在更大规模上再来一轮

用这个技能时，你的工作是判断用户现在处在这个流程的哪一步，然后把他往前推。比如用户说"我想做一个处理 X 的技能"，你可以帮他把需求收窄、写草案、写测试用例、确定评估方式、跑完所有 prompt 然后再来一轮。反过来，如果用户已经有草案了，直接进入评测与迭代环节。

当然，永远保持灵活：用户要是说"我不想跑一堆评测，你先陪我聊聊思路就行"，那就照办。

技能基本成型之后（顺序依然可以灵活），还可以跑一下描述优化器——那是单独一个脚本，专门提升技能的触发准确率。

## 确认意图

先弄清楚用户到底想要什么。对话历史里可能已经包含一个用户想固化成技能的工作流（比如"把这个变成技能"）。这种情况下先从上下文里就地提取答案：用过哪些工具、步骤顺序是什么、用户在哪儿纠正过你、输入输出长什么样。剩下的空缺再问用户，并在他确认之后再进入下一步。

1. 这个技能要让 agent 能做什么？
2. 什么时候该触发？（用户会说什么话、在什么场景）
3. 期望的输出形式是什么？
4. 要不要建测试用例来验证？输出可以客观验证的技能（文件转换、数据抽取、代码生成、固定的流程步骤）很适合建用例；输出偏主观的技能（写作风格、美术）往往不需要。按技能类型给出合适建议，但让用户决定。

## 访谈与研究

主动问边界情况、输入输出格式、示例文件、成功标准和依赖。把这些捋顺了再写测试 prompt。

检查有哪些可用的 MCP 工具。如果对调研有帮助（查文档、找相似技能、查最佳实践），并行调研；有子智能体能力就交给子智能体，没有就在主对话里做。带着上下文来，减少用户的负担。

## 写 SKILL.md

基于访谈，把这些部分填上：

- **name**：技能标识，kebab-case，最多 64 字符
- **description**：何时触发、做什么。这是唯一的触发机制——既要写清技能做什么，也要写清具体在什么场景用。所有"什么时候用"的信息都放这里，不要放到正文。注意：agent 普遍"触发不足"，该用的时候不用。为了对抗这一点，描述可以写得**稍微主动一点**。比如不写"如何做一个展示公司数据的简易仪表盘"，而是写"如何做一个展示公司数据的简易仪表盘。用户提到仪表盘、数据可视化、内部指标，或想展示任何形式的公司数据时都应当使用本技能，即使他没有明确说出『仪表盘』这个词。"
- **metadata.language**：本技能的语言标签（见「多语言版本」一节）
- **compatibility**：需要的工具与依赖（可选，很少需要）
- **正文和其余部分**

### 技能写作指南

#### 一个技能的解剖

```
skill-name/
├── SKILL.md （必需）
│   ├── YAML frontmatter（name、description 必需）
│   └── Markdown 指令
└── 捆绑资源（可选）
    ├── scripts/    - 用于确定性/重复性任务的可执行代码
    ├── references/ - 按需加载进上下文的文档
    └── assets/     - 用于产出物的文件（模板、图标、字体）
```

#### 渐进式披露

技能用三级加载：
1. **元数据**（name + description）——始终在上下文里（约 100 词）
2. **SKILL.md 正文**——技能被触发时进入上下文（理想情况下少于 500 行）
3. **捆绑资源**——按需加载（不限量；脚本可以直接执行而不载入上下文）

这些字数是经验值，确有需要可以更长。

**关键做法：**
- SKILL.md 保持在 500 行以内；接近上限时再加一层目录结构，并在正文里写清"接下来该去看哪个文件"
- 从 SKILL.md 明确引用参考文件，并说明什么情况下读它
- 超过 300 行的参考文件，开头加一个目录

**按领域组织**：当一个技能覆盖多个领域/框架时，按变体拆分：

```
cloud-deploy/
├── SKILL.md （流程 + 选择逻辑）
└── references/
    ├── aws.md
    ├── gcp.md
    └── azure.md
```

agent 只会读相关的那一份。

#### 不许有意外

技能里不能有恶意代码、漏洞利用代码，或任何可能危害系统安全的内容。技能一旦被采用，其内容不应该在意图上让用户感到意外。不要配合"做一个误导性的技能"或"专为未授权访问、数据外泄等恶意目的设计"的请求，也不要为了让用户满意而装作看不出问题。"扮演某个角色"这类是没问题的。

#### 写法

指令优先用祈使句。

**定义输出格式**——可以这样写：

```markdown
## 报告结构
始终使用下面这个模板：
# [标题]
## 摘要
## 主要发现
## 建议
```

**示例法**——示例很有用，可以这样写（如果示例里同时有 Input 和 Output，你可能想把它们改成更贴切的名字）：

```markdown
## Commit message 格式
**示例 1：**
输入：给用户认证加上 JWT 令牌
输出：feat(auth): implement JWT-based authentication
```

#### 写作风格

尽量说明**为什么**重要，而不是堆砌咄咄逼人的"必须/绝不"。今天的模型很聪明，有不错的心理理论能力，给出好的约束条件后能自己举一反三。所以先写一版草案，再换一副新眼睛看一遍去改。

把技能写得**通用**一点，别过度贴合手头这几个例子。

### 测试用例

写完草案后，想 2-3 个真实场景的测试 prompt——真人用户真的会这么说的那种。跟用户过一遍（不必照抄我的措辞）："我打算先试这几个用例，你看合适吗？还想补什么？"然后跑。

测试用例存到 `evals/evals.json`。先只写 prompt，别急着写断言，断言在下一节里趁着跑测试的间隙再起草。

```json
{
  "skill_name": "example-skill",
  "evals": [
    {
      "id": 1,
      "prompt": "用户的任务 prompt",
      "expected_output": "对期望结果的描述",
      "files": []
    }
  ]
}
```

完整 schema（包括稍后才加的 `assertions` 字段）见 `references/schemas.md`。

## 跑测试用例并评估

这一节是一个连续的序列，不要半路停下。

结果放在 `<skill-name>-workspace/`，与技能目录同级。目录结构是约定好的，因为汇总脚本按这个形状扫描——少一层就拿不到数据：

```text
<skill-name>-workspace/
└── iteration-1/
    ├── csv-column-tidy/            ← 用例目录，用描述性名字
    │   ├── eval_metadata.json
    │   ├── with_skill/
    │   │   ├── run-1/
    │   │   │   ├── outputs/        ← 产出文件
    │   │   │   ├── grading.json
    │   │   │   └── timing.json
    │   │   └── run-2/              ← 同一配置重复跑时才需要
    │   └── without_skill/
    │       └── run-1/
    │           ├── outputs/
    │           └── grading.json
    └── pdf-table-extract/
        └── …
```

要点：
- 用例目录名可以（也应该）用描述性名字，不必叫 `eval-0`
- **每个配置下面必须有 `run-<N>/` 这一层**，`grading.json` 放在 run 目录里
- 只跑一次就是 `run-1`；跑多次用 `run-1`、`run-2`，汇总时会算均值和标准差
- 不必一次把目录建全，用到再建

`python -m scripts.aggregate_benchmark` 正是按 `<用例>/<配置>/run-<N>/grading.json` 扫描。形状不对时它会明确报错退出，而不是生成一份全零的基准。

### 第一步：在同一轮里把所有 run 都发出去

每个测试用例要跑两个 run——一个装了技能，一个作为基线。重点在于：不要先把装技能的跑完再回头补基线，同时发出去，让它们差不多同时结束。

**装技能的 run：**

```
执行这个任务：
- 技能路径：<path-to-skill>
- 任务：<eval prompt>
- 输入文件：<eval 的 files，没有就写 none>
- 输出保存到：<workspace>/iteration-<N>/<用例名>/with_skill/run-1/outputs/
- 需要保存的产出：<用户真正关心的东西，例如"那个 .docx 文件"、"最终 CSV">
```

**基线 run**（prompt 相同，基线取什么取决于场景）：
- **新建技能**：完全不用技能。同样的 prompt，不给技能路径，存到 `without_skill/run-1/outputs/`
- **改进已有技能**：用旧版本。动手前先快照（`cp -r <skill-path> <workspace>/skill-snapshot/`，Windows 上用 `Copy-Item -Recurse`），再让基线 run 指向快照，存到 `old_skill/run-1/outputs/`

为每个测试用例写一个 `eval_metadata.json`（断言先留空）。按它测的内容起个有描述性的名字，别就叫 "eval-0"。目录名也用这个名字。如果这一轮用了新增或修改过的 prompt，要为每个新的 eval 目录都建这个文件，不要假定上一轮的能沿用。

```json
{
  "eval_id": 0,
  "eval_name": "descriptive-name-here",
  "prompt": "用户的任务 prompt",
  "assertions": []
}
```

**关于怎么"发出去"**：取决于你的运行环境。有并行子智能体就每个 run 一个（例如 Finch 的 `multi_agent_run`、某些 CLI 的 task/subagent 工具）；没有就串行跑，或者直接在主对话里按技能指令做一遍。见「不同环境怎么适配」一节。无论用哪种方式，两个要点不变：装技能和不装技能要公平对比，每个 run 的产出要落到各自的 `outputs/` 目录。

### 第二步：跑的同时起草断言

别干等。用这段时间给每个测试用例草拟可量化的断言，并跟用户解释清楚。如果 `evals/evals.json` 里已经有断言，就复查并说明它们在检查什么。

好的断言是可客观验证的，名字要有描述性——在基准报告里扫一眼就能明白它在检查什么。主观类技能（写作风格、设计质量）更适合定性评估，不要硬套断言。

草拟完把断言更新到 `eval_metadata.json` 和 `evals/evals.json` 里。同时也跟用户说清楚接下来在浏览器里会看到什么——既有定性的产出，也有定量的基准。

### 第三步：run 陆续完成时，立刻记下耗时

每个 run 结束时都应当拿到 token 总量和耗时。如果运行环境提供了这些数字（任务完成通知、日志、你自己的计时），立刻写进该 run 目录下的 `timing.json`：

```json
{
  "total_tokens": 84852,
  "duration_ms": 23332,
  "total_duration_seconds": 23.3
}
```

这一步容易漏，而且事后补不回来。**拿不到精确数据就别编**：把已知的字段留下（哪怕只有用自己的计时），未知的省略。基准报告缺一列，比有一列假数字好得多。

### 第四步：评分、汇总、打开查看器

全部 run 结束后：

1. **逐个评分** —— 让一个评分 agent（或你自己在主对话里）读 `agents/grader.md`，对每个断言逐条核对产出，结果存到各 run 目录的 `grading.json`。`grading.json` 的 expectations 数组必须用 `text`、`passed`、`evidence` 这三个字段名（不是 `name`/`met`/`details` 之类的变体），查看器依赖这几个确切的名字。能用脚本检查的断言就写脚本跑，比肉眼判断更快、更可靠，跨迭代还能复用。

2. **汇总成基准** —— 从技能目录运行汇总脚本：
   ```bash
   python -m scripts.aggregate_benchmark <workspace>/iteration-N --skill-name <name>
   ```
   会生成 `benchmark.json` 和 `benchmark.md`，含每种配置的 pass_rate、耗时、token，以及均值 ± 标准差和差值。手工写 benchmark.json 时，字段名严格照 `references/schemas.md`。把装技能的版本排在对应基线前面。

3. **做一遍分析** —— 读基准数据，把汇总统计掩盖掉的模式挑出来。看什么，见 `agents/analyzer.md` 里"分析基准结果"一节：比如无论装不装技能都通过的断言（没有区分度）、方差过高的用例（可能不稳定）、耗时与 token 的取舍。

4. **打开查看器**，同时展示定性产出和定量数据：
   ```bash
   python <skill-creator-path>/eval-viewer/generate_review.py \
     <workspace>/iteration-N \
     --skill-name "my-skill" \
     --benchmark <workspace>/iteration-N/benchmark.json
   ```
   第 2 轮及以后，再加 `--previous-workspace <workspace>/iteration-<N-1>`。

   **没有显示器或浏览器的环境**（远程服务器、容器、沙箱）：改用 `--static <output_path>` 生成一个独立的 HTML 文件，然后把路径给用户让他自己打开。用户点"Submit All Reviews"时 `feedback.json` 会以文件形式下载；下载完把 `feedback.json` 拷回工作区目录，供下一轮使用。

   请用 `generate_review.py` 生成查看器，不要自己另写一套 HTML。

5. **告诉用户**（大意）："结果已经在浏览器里打开了。有两个标签页——『Outputs』可以逐个点开测试用例留反馈，『Benchmark』看定量对比。看完回来跟我说一声。"

### 用户在查看器里看到什么

"Outputs" 标签页一次展示一个测试用例：
- **Prompt**：给的任务
- **Output**：技能产出的文件，能内联渲染的会直接渲染
- **Previous Output**（第 2 轮起）：折叠显示上一轮的产出
- **Formal Grades**（如果跑过评分）：折叠显示断言通过情况
- **Feedback**：随输入自动保存的文本框
- **Previous Feedback**（第 2 轮起）：上次的评论，显示在文本框下方

"Benchmark" 标签页显示统计汇总：各配置的通过率、耗时、token 用量，含逐用例拆解和分析观察。

翻页用按钮或方向键。看完点 "Submit All Reviews"，所有反馈会保存到 `feedback.json`。

### 第五步：读反馈

用户说看完了，就读 `feedback.json`：

```json
{
  "reviews": [
    {"run_id": "eval-0-with_skill", "feedback": "图表缺了坐标轴标签", "timestamp": "..."},
    {"run_id": "eval-1-with_skill", "feedback": "", "timestamp": "..."},
    {"run_id": "eval-2-with_skill", "feedback": "完美，就喜欢这样", "timestamp": "..."}
  ],
  "status": "complete"
}
```

反馈留空表示用户觉得没问题。把改进集中在用户明确提了意见的用例上。

用完记得关掉查看器服务（如果用 `--static` 就没这回事）。

## 改进技能

这是整个循环的核心。测试跑完了，用户看过结果了，现在根据反馈把技能改得更好。

### 怎么想改进

1. **从反馈里提炼一般规律。** 大的图景是：我们要做的是能被用一百万次（也许更多）的技能，而这里只反复迭代了几个例子。用户对这几个例子烂熟于心，评估新产出很快，这对提速很有帮助。但如果技能只在这几个例子上好用，它就是废的。与其塞进讨好式的、过拟合的小改动，或者压得人喘不过气的"必须"，不如换个比喻、换个工作方式来试——试错很便宜，说不定就撞上好东西。

2. **保持精简。** 删掉不承重的部分。要看**过程记录**，不是只看最终产出。如果技能让模型浪费大量时间做无用功，试着把导致这些行为的部分删掉，看看会怎样。

3. **解释为什么。** 对自己要求的一切尽量都说清**原因**。如果发现自己在写全大写的"始终/绝不"，或使用极其僵硬的结构，这是个警示信号——能重新表述就重新表述，把道理讲明白。

4. **找跨用例的重复劳动。** 读测试运行的记录，看是不是每个 run 都各自写了一份相似的辅助脚本，或者用同样的多步办法解决同一件事。如果 3 个用例里有 3 个都在写 `create_docx.py` 或 `build_chart.py`，这就是明确的信号：技能该把这个脚本打包进去。写一次，放进 `scripts/`，让技能去用它。这样以后每次调用都不用重新造轮子。

这件事很重要（我们的目标是每年创造可观的价值），思考时间不是瓶颈，慢下来好好琢磨。建议先写一版修订，然后再用新眼睛看一遍去改，尽力钻进用户的脑子里，弄明白他到底想要什么。

### 迭代循环

改进之后：

1. 把改进应用到技能上
2. 把所有测试用例重跑到新的 `iteration-<N+1>/` 目录，包括基线 run。新建技能时基线永远是 `without_skill`（不装技能），跨迭代保持不变；改进已有技能时，自行判断基线取哪个更合理：是用户带来的最初版本，还是上一轮的版本
3. 打开复查器，用 `--previous-workspace` 指向上一个迭代
4. 等用户看完并告知
5. 读新的反馈，再改进，再来一轮

什么时候停：
- 用户说满意了
- 反馈全是空的（都看着不错）
- 已经没有实质性进展

## 进阶：盲测对比

需要更严格地比较两个版本的技能时（例如用户问"新版真的更好吗？"），有套盲测机制。细节见 `agents/comparator.md` 和 `agents/analyzer.md`。基本思路：把两份产出交给一个独立的 agent，不告诉它哪份是哪份，让它评判质量；然后分析赢家为什么赢。

这是可选项，依赖子智能体，多数用户用不上。人工复查这一环通常就够了。

## 描述优化

`SKILL.md` frontmatter 里的 description 是决定 agent 是否会加载技能的主要机制。技能新建或改进完之后，可以提议优化描述以提升触发准确率。

### 第一步：生成触发测试查询

造 20 条测试查询——该触发的和不该触发的混在一起。存成 JSON：

```json
[
  {"query": "用户的 prompt", "should_trigger": true},
  {"query": "另一个 prompt", "should_trigger": false}
]
```

查询必须真实，是这个 agent 的用户真的会打出来的话。不要抽象请求，要具体、有细节：文件路径、用户自己的职业和处境、列名和取值、公司名、URL，带一点背景故事。有的可以是全小写，带缩写、错别字或口语。长度要混，重点放在边界情况上，别都做成一眼就能判断的（用户会有机会签字确认）。

差：`"格式化一下这些数据"`、`"从 PDF 里抽文本"`、`"做张图"`

好：`"我老板刚发我一个 xlsx（就在下载文件夹，好像叫『Q4 销售 最终 最终版 v2.xlsx』），她要我加一列算利润率的百分比。收入好像是在 C 列，成本在 D 列"`

**该触发的**（8-10 条）要有覆盖面：同一个意图的不同说法，有的正式有的随意；包括用户没直接说技能名或文件类型、但明显需要它的场景；掺一些不太常见的用法；再来一些与其他技能竞争、但本技能应该赢的场景。

**不该触发的**（8-10 条）最有价值的是"擦边"查询——和技能共享关键词或概念，但实际需要的是别的东西。想想相邻领域、天真的关键词匹配会误触发但其实不该触发的模糊表达，以及查询确实碰到了技能的能力范围、但在那个场景里用别的工具更合适的情况。

最要避免的是：把不该触发的查询做得显而易见无关。"写一个斐波那契函数"作为 PDF 技能的负样本太容易了，什么也没测到。负样本要真的刁钻。

### 第二步：让用户过一遍

用 HTML 模板把测试集呈现给用户复查：

1. 读 `assets/eval_review.html`
2. 替换占位符：
   - `__EVAL_DATA_PLACEHOLDER__` → 测试条目的 JSON 数组（不加引号，它是一条 JS 变量赋值）
   - `__SKILL_NAME_PLACEHOLDER__` → 技能名
   - `__SKILL_DESCRIPTION_PLACEHOLDER__` → 技能当前的 description
3. 写到临时文件并打开：
   - macOS：`open /tmp/eval_review_<skill-name>.html`
   - Windows：`Start-Process <path>`
   - Linux：`xdg-open <path>`
4. 用户可以改查询、切换该不该触发、增删条目，然后点 "Export Eval Set"
5. 文件会下载到下载目录——如果出现多个（如 `eval_set (1).json`），挑最新的那个

这一步很重要：查询造得不好，描述就优化不好。

### 第三步：跑优化循环

跟用户说："这个要跑一会儿，我在后台跑优化循环，会时不时看进度。"

把测试集存到工作区，然后在后台运行：

```bash
python -m scripts.run_loop \
  --eval-set <path-to-trigger-eval.json> \
  --skill-path <path-to-skill> \
  --agent auto \
  --max-iterations 5 \
  --verbose
```

`--agent auto` 会自动挑 PATH 上第一个可用且受支持的 CLI。要用别的、或要传模型：

```bash
# 指定预设
python -m scripts.run_loop ... --agent codex

# 任何自定义 CLI：告诉它怎么收 prompt
python -m scripts.run_loop ... --agent-cmd "my-agent --print {prompt}"

# 该 CLI 从 stdin 读 prompt
python -m scripts.run_loop ... --agent-cmd "my-agent --print" --agent-transport stdin

# 模型（只在 CLI 支持时传）
python -m scripts.run_loop ... --model <model-id>
```

`{prompt}` 是占位符；模板里没有它时，prompt 会作为最后一个参数追加。也可以用环境变量 `SKILL_CREATOR_AGENT_CMD` 代替 `--agent-cmd`。

脚本会自动跑完整循环：把测试集按 60% 训练 / 40% 留出测试切分，评测当前的描述（每条查询跑 3 次以获得可靠的触发率），然后让 agent 根据失败项提出改进。每个新描述都在训练集和测试集上重新评测，最多迭代 5 次。跑完会打开一个 HTML 报告显示各轮结果，并返回 JSON，其中 `best_description` 是按测试集得分而不是训练集得分选的，避免过拟合。

跑的时候定期看看输出，告诉用户当前第几轮、分数如何。

### 触发是怎么发生的

理解触发机制有助于设计更好的测试查询。技能以"名字 + 描述"的形式出现在 agent 的技能清单里，agent 只根据这份描述判断要不要去查技能。关键是：agent 只在任务超出自己直接处理能力时才去查。像"读一下这个 PDF"这种简单的一步请求，描述再准也可能不触发，因为 agent 自己就能干。复杂、多步、专业性强，才在描述匹配时可靠地触发。

所以测试查询要有实质内容，足以让 agent 真的从技能中受益。"读一下文件 X"是很差的测试用例，无论描述写得多好都不会触发。

### 第四步：应用结果

从输出的 JSON 里取 `best_description`，更新技能 SKILL.md 的 frontmatter。把前后对比和分数报给用户。

## 打包与交付

想交付一个可分发的技能包时（只有当运行环境有把文件交给用户的能力时才做这一步；没有就跳过）：

```bash
python -m scripts.package_skill <path/to/skill-folder>
```

打包后把生成的 `.skill` 文件路径告诉用户，方便他安装。

## 不同环境怎么适配

主流程（草案 → 测试 → 复查 → 改进 → 再测试）在各处都一样，只是机制不同。先判断自己处在哪种环境，再按下面调整。判断方法：能不能并行开子智能体？有没有显示器？agent CLI 可不可用？

### 有并行子智能体

最理想的情况。所有测试用例可以真的并行跑，基线对比也有意义，可以完整地做定量基准。

- 每个测试用例开两个子智能体（装技能 / 基线），同一轮里全发出去
- 让子智能体自己记录 `metrics.json`（工具调用次数、产出字符数、遇到的错误数），评分时用得上
- 如果遇到严重超时问题，串行跑也可以接受

### 没有子智能体（单线程，例如网页版对话或单进程 CLI）

- 并行不了就一个个来。对每个测试用例，先读技能的 `SKILL.md`，然后照着它把 prompt 做完。比独立子智能体要不严格（技能是你写的，跑的时候又带着全部上下文），但作为基本检查有用，而且后面的人工复查这一环能补上
- **跳过基线 run**——没有独立执行，基线对比没有意义
- **跳过定量基准**——同理。把力气放在用户的定性反馈上

### 没有浏览器或显示器

- 生成查看器时用 `--static <output_path>`，写一个独立 HTML 文件，把路径给用户，让他自己打开
- 完全没法给用户看 HTML 时，直接在对话里呈现结果：每个测试用例给出 prompt 和产出。如果产出是文件（比如 .docx、.xlsx），存到文件系统并告诉用户路径，让他下载查看。就地征求意见："这样看着怎么样？有什么想改的？"

### agent CLI 不可用

触发相关的量化功能（把描述改成任意 CLI 都能传的模板）需要能非交互调用一个 agent CLI。不可用时：

- 描述优化整节跳过
- 测试用例仍可跑，但只能在主对话里手工做，分数靠人工判断
- 技能的写作、评测设计、打包都不受影响

### 以 Claude Code / Claude.ai / Cowork 为主要工具时

上游原始版本就是为这些环境写的，你需要知道的差异：

- **Claude Code**：主流程完整可用。`--agent claude` 是默认预设之一，`auto` 通常也会选中它。压缩后的 `.skill` 文件可以直接分享
- **Claude.ai**：没有子智能体，也没有 `claude` CLI 的非交互调用，按上面两节减配执行。`package_skill.py` 照样能用，只要有的 Python 和文件系统
- **Cowork**：有子智能体，主流程能跑；没有显示器，查看器用 `--static`。注意：这类环境里的 agent 常常会不自觉地在测试跑完后跳过生成查看器，所以再强调一次——**无论在哪种环境，跑完测试都要先用 `generate_review.py` 生成查看器让人看样本，再自己去评估和修改技能**。用现成脚本，别自己写一份花哨的 HTML。这一步的目的就是把东西尽快摆到人眼前

### 更新已有技能

用户也可能是让你改已有技能，而不是新建。这时：

- **保留原名。** 记下技能目录名和 frontmatter 里的 `name`，原样沿用。比如装好的技能叫 `research-helper`，产出就应该叫 `research-helper.skill`（不是 `research-helper-v2`）
- **先拷到可写位置再改。** 已安装的技能路径可能是只读的。拷到临时目录，在那里改，从副本打包
- **手工打包时先在临时目录里做好**，再拷到输出目录——直接写目标位置可能因权限失败

## 多语言版本

本技能遵循双语技能仓库的规则，中英文两版都独立可用。下面是组织、优先级、同步与发布上的要求。当这些规则与上面的技能编写指令冲突时，**技能实现部分以上面的编写指令为准**，同时保留本节的中英双语要求。

### 一、语言结构

每个技能仓库**必须**使用下面的目录结构：

```text
skill-name/
├── zh-CN/
│   └── skill-name/
│       ├── SKILL.md
│       ├── scripts/
│       ├── references/
│       └── assets/
│
├── en-US/
│   └── skill-name/
│       ├── SKILL.md
│       ├── scripts/
│       ├── references/
│       └── assets/
│
├── README.md
├── LICENSE
└── .gitignore
```

- `zh-CN/`：简体中文版。
- `en-US/`：美式英语版。
- 两个语言目录**必须**各自包含一个可独立使用的技能。
- 两个版本**必须**使用同一个技能名。
- 可选目录**应当**只在需要时才创建。

### 二、开发优先级

简体中文是主要开发语言。

1. **始终**先创建并开发简体中文版。
2. 中文版完成实现、验证和修订之后，再进行翻译。
3. 基于已验证的中文版创建或更新美式英语版。
4. **绝不**在美式英语版里独立引入功能或行为变更。
5. 不要为了准备美式英语版而拖延中文开发。

### 三、内容同步

两个语言版本**必须**在功能和行为上保持一致。

- 指令、工作流、约束、权限和安全要求应保持等价。
- 脚本、资源、模板和其他功能性资源应保持同步。
- 美式英语的措辞**可以**为自然可读性做调整，但不得改变含义。
- 中文版的任何功能变更**必须**触发英文同步复查。
- 缺陷修复和安全更新**必须**在两个版本中都体现。
- 翻译过程中**绝不**悄悄删除或弱化要求。

### 四、元数据与版本

每个 `SKILL.md` **必须**保留 Agent Skills 的标准元数据要求。

两个语言版本使用相同的技能名和版本号。

语言元数据**应当**按以下方式声明：

中文：

```yaml
metadata:
  language: zh-CN
```

美式英语：

```yaml
metadata:
  language: en-US
```

维护版本元数据时，两个版本**必须**使用相同的版本号。

### 五、独立性与依赖

- 每个语言版本**必须**可以独立安装和分发。
- **绝不**跨语言目录引用文件。
- 所有资源引用**必须**使用相对于对应技能目录的路径。
- 不要要求用户同时下载两个语言版本。
- 不要在各自技能目录之外重复放置共用的功能性依赖。

### 六、README 与发布

- 仓库级 `README.md` **应当**提供概览，并明确标示两个语言版本。
- 每个语言版本作为独立的技能目录发布。
- 发布过程**必须**保留技能目录结构。
- 不要假定每个 Agent 都会自动发现嵌套的语言目录。
- 发布前先确认目标 Agent 的技能发现与安装行为。

### 七、规则优先级

这些规则只管辖双语组织、语言优先级、同步与分发。

专门的技能编写指令仍然负责技能设计、内容创作、格式与校验。

冲突时，技能实现遵循专门的技能编写指令，同时保留本节定义的双语要求。

  - 跑定量评测

- 打包最终技能，交付给用户
