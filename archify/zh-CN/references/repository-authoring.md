# 基于仓库的架构编写 <a id="repository-backed-architecture-authoring"></a>

当一幅图必须解释一个真实仓库时，使用本参考。源码是职责、调用、边界与持久化的权威。当所请求的含义已被覆盖，且每条被断言的事实都有来源证据支撑时，这幅图便算完整。

## 按需探索 <a id="explore-on-demand"></a>

1. **冻结身份。** 从目标仓库记录 `git rev-parse
   HEAD`、`git remote get-url origin` 和 `git status --short`。在记录 origin 或把它放进候选图之前，移除 HTTP(S) userinfo（包括用户名、密码和令牌）。保留其传输方式、端口、路径和 `.git` 后缀；不要把内部 SSH origin 改写为 HTTPS。把不含凭据的 URL 与四十字符的 revision 固定在 `meta.repository`。对于 SSH origin、不支持的托管平台、刻意仅本地（local-only）的来源链接，或一个其 HTTPS URL 只是仓库身份标识的本地夹具，使用 `link_mode: "local-only"`；保留 URL 与 revision。Web 链接要求受支持的 GitHub 或 Gitee HTTPS origin。若工作树是脏的，记录被改动的路径。仓库证据是按固定 revision 的已提交字节来验证的，而不是按工作树改动：对于任何被引用的改动路径，检视该 revision 上的干净检出。不要把未提交的字节当作 `HEAD` 的证据；`local-only` 不会记录这些字节的可验证快照。

2. **映射切片。** 使用项目说明、清单（manifest）、入口点、注册项与部署配置来定位候选运行时单元。阅读与请求相关的入口、配置与模块。顺着 import 与调用点，直到所请求的职责抵达其真实输入、输出或副作用。阅读一个小的连通切片，而不是为了一个方便的标签而扫描整个仓库。

3. **追踪归属。** 从调用点处观察到的参与者、操作和对象，推导运行时与 I/O 关系；部署与信任关系则使用相应的配置或执行证据。区分请求某项操作的控制方与执行它的运行时，以及接收字节的存储。对于文件或数据库边，来源必须指明其真实的读取方或写入方；“维护任务”之类的职责陈述并不证明直接 I/O。在阅读时把这些事实与来源位置保持在一起，无需另建规划产物。用 [构图与含义](authoring-defaults.md#composition-and-meaning)来选择哪些区分需要单独的节点；发现一个实现角色并不会自动把它加进总览。一个已配置的 provider、一个注入的 adapter、一个本地 stub 与一个持久服务是不同的断言；为你所依据的来源所支持的那一个打标签。

4. **边读边记录证据。** 为每个组件和有意义的关系保留精确的、相对于仓库的路径与闭区间行范围。顺着真实的分支、重试、回退与错误处理。一个被导出或被配置但从未在正常路径上被调用的函数，是可选能力，而不是必需的运行时边。对于关于权威状态变更或控制权归属的断言，追踪到真正的写入或执行位置，以及允许它的条件；仅凭一个上游调用方并不能确立那些条件。

5. **命名不确定性。** 把未解决的问题写在它们所影响的断言旁边：例如，“`writeFile` 在这里被调用；持久性未知。”通过阅读下一段相关源码范围来解决一个问题，或把它保留为一个显式未知项。绝不要把标签、包描述或配置值变成未被观察到的服务或行为。

当每个被请求的职责、关系与边界都有来源蕴含支撑，且其余未知项无法改变该覆盖范围时，就停止探索。节点、边、引用、视图、卡片或边界都没有配额要达成。不要仅仅为了示意完成而添加一个总结步骤。

在已知时批量阅读相互独立的、相关的文件。每次额外的阅读都应回答一个能改变该图的问题。复用本任务中已核验过的简洁事实及其来源范围；跨 revision 时，重新核对受影响的入口点、配置、依赖与证据。

## 按结构选择示例 <a id="choose-an-example-by-structure"></a>

在加载其内容之前，使用请求与已为源码检视所需的仓库元数据，在 [类型路由](../SKILL.md#type-router) 中选出主示例。选择应契合现有的阅读批次，且不需要额外的消息、命令或全仓库扫描。对于混合或不明确的任务，使用在常规检视中逐渐得知的所请求职责与入口点；保留它们的真实角色。当某项必要能力仍未被解释时，阅读另一个示例。示例教授的是形状，而非事实：库不必获得文件系统节点，已完成的展示样例也仍遵循初稿的自动走线规则。

## 基于证据编写 <a id="author-from-evidence"></a>

使用该模式完整的 JSON 形状，包括仓库身份、组件与连接；每个基于仓库的组件都需要有来源引用支撑，而边界或卡片只有在回答读者真实问题时才添加。先让自动走线与自动 viewBox 尺寸发挥作用。让主路径保持可读，把异常路径放在其拥有者旁边，并在来源显示存在独立职责时，把文件系统存储留在一个控制边界之外。

一个既有示例教授的是字段形状，而非事实或任意取值。它并不授权新的边界种类、一条很长的注释、一个 viewBox 尺寸或一项走线控制。无论所选示例是否已包含该字段，都要查阅该模式的 schema 与 `schemas/common.schema.json`；使用 schema 的枚举、长度、标识符与仓库规则。Architecture 边界当前使用 `kind: "region"` 或 `kind: "security-group"`；来源引用使用 `path`、`line` 和可选的 `end_line`。

基于仓库的组件需要简洁、真实的 `sources` 引用。在总结文件系统 I/O 时保留控制权归属：读取或写入文件的代码拥有该动作，而纯粹的内存内变换只接收并返回值。这一事实核查并不要求为每个 helper 单独建一个总览节点。使用既有示例来获得合法的字段形状，然后用检视到的仓库事实替换所有标识符、措辞、来源路径与断言。
