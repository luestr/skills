# Architecture 布局修复 <a id="architecture-layout-repair"></a>

当实际视觉审查发现若干缠结的走线之后，使用本文件。一份成功的机器凭据（receipt）并不确定构图。在既有候选图上工作，保留所有必需的组件、关系、标签、证据、边界与节点尺寸。

## 选择修复范围 <a id="choose-the-repair-scope"></a>

若主链与次链已清晰可读，就在局部修复孤立的缺陷。若某条主链被阻断、若干走线缠结，或某处局部修复把缺陷挪到了另一条走线上，就在一次编辑中重排整个连通场景。保留所有语义与用户固定的几何；Agent 生成的位置与走线控制可以改变。移动节点后，移除过时的生成式走线覆盖，让自动走线能使用新的摆位。

凭据的 `directCorridorBlockers`（若存在）会指出位于某条边的对齐端点之间的节点。这是几何证据，并不是该边属于主路径的证明，也不代表新的校验失败。先追踪读者真正的主路径。当所列的某个 blocker 中断了那条路径时，重排该连通分组，而不是再加一条绕行。

## 一次连贯的修复 <a id="one-coherent-repair"></a>

1. 在 JSON 中追踪受影响的关系及其端点。在选择坐标之前，把读者的主路径写成一个由现有边组成的有序列表，然后标出共享状态与真实的反馈环。该主路径中每一对相邻节点都必须有正在被解释的那种关系；把其他组件放在其真实拥有者旁边的分支上。如果紧凑凭据与截图未揭示所需的走线或标签几何，则运行一次 `validate architecture <candidate.json> --layout-json --repo-root <root>`；仅对没有仓库证据的设计才省略 `--repo-root`。不要猜测重复的 waypoint 坐标。
2. 按阅读顺序摆放那些相连的主路径邻居节点。把共享状态放在其读取方/写入方之间，必要时放在相邻的一行，使单个写入方无需一条跨越整个执行区域的线。把一个反馈环按其真实的边顺序围绕一个开放的矩形排列，其他消费方放在其拥有者旁边。例如，若边为 `client → API → dispatcher → worker → collector → runner → dispatcher`，就把前四个放在上行，collector 放在 worker 下方，runner 放在 dispatcher 下方：这样回流就使用下行并配一条短的上行边。这示范的是相邻性，而不是一张要照抄的图或一组坐标；只使用候选图中存在的关系。保留每条边及其真实方向。
3. 为新摆位保留自动端点。仅当某条分支或回流需要一条特定走廊时才约束某一侧；针对每条受影响的关系（包括存储分支）检查该走廊。若该局部约束引入了另一个冲突，就回到连通摆位，而不是在侧的组合同循环反复。只对剩余的实测缺陷使用详细的 `via` 或标签坐标。让外部参与者保持在已解决的边界矩形之外，包括其内边距；未把某节点列入 `wraps` 并不会在视觉上排除它。把内部关系及其标签保持在共享边界内，除非跨越它能传达一个真实事实；不要仅为避免另一条走线而暗示一次外部的跳转。
4. 当 `composition/label-gap` 报告一个实测最小值时，扩大该净空，或把该连通分组移到另一可读的行。把完整标签保持在其自己的走线旁；把它放进远处的空白不会修复该关系。在保留实测标签空间与先前文本大小的同时，压缩未使用的空隙。让主要交互与所有必需节点在默认桌面视图中保持可读；不要为减少交叉而换来巨大的空白画布、极小的文本，或一条没有语义理由而折返的链。

编辑后运行一次完整的 `finalize`，然后对成功的产物运行 `visual-check`，并检视其桌面截图。在替换一个已审查过的产物时，为两条命令使用同一个全新的 `--out-dir`，如 [交付契约](delivery-contract.md#a-new-candidate-at-an-existing-output-path)所述。追踪主路径、每条次链，以及每个受影响的箭头与标签。一次有界的第二次修复可以处理某个剩余的特定缺陷。若它仍未通过视觉验收，保留该候选图并报告具体的差距；不要把它算作一次成功的修复，也不要继续盲目地改坐标。
