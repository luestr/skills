# 领域建模

设计时主动构建并打磨项目的领域模型。这是一项*主动*的纪律：质疑术语、构造边界场景，并在术语表和决策一成型就立刻写下来。（仅仅为了查词而*读* `GLOSSARY.md` 不算本技能：那是任何技能都能做到的一行习惯。本技能针对的是你在改变模型的时候，而不只是消费它的时候。）

## 文件结构

多数仓库只有一个上下文：

```
/
├── GLOSSARY.md
├── docs/
│   └── adr/
│       ├── 0001-event-sourced-orders.md
│       └── 0002-postgres-for-write-model.md
└── src/
```

如果根目录存在 `GLOSSARY-MAP.md`，说明仓库有多个上下文。这个映射文件指出每个上下文的位置：

```
/
├── GLOSSARY-MAP.md
├── docs/
│   └── adr/                          ← 系统级决策
├── src/
│   ├── ordering/
│   │   ├── GLOSSARY.md
│   │   └── docs/adr/                 ← 上下文专属决策
│   └── billing/
│       ├── GLOSSARY.md
│       └── docs/adr/
```

按需创建文件：只有有东西要写时才创建。如果没有 `GLOSSARY.md`，就在第一个术语敲定时创建它。如果没有 `docs/adr/`，就在需要第一条 ADR 时创建它。

## 会话过程中

### 对照术语表提出质疑

当用户使用的术语与 `GLOSSARY.md` 中既有的语言冲突时，立刻指出。“你的术语表把 ‘cancellation’ 定义为 X，但你说的似乎是 Y。到底是哪个？”

### 打磨含糊的语言

当用户使用含糊或含义过载的术语时，提出一个精确的规范术语。“你说的是 ‘account’：你指的是 Customer 还是 User？这是两回事。”

### 讨论具体场景

讨论领域关系时，用具体场景对它们做压力测试。构造能探查边界情况、并迫使用户精确说明概念之间边界的场景。

### 与代码相互对照

当用户陈述某个东西如何工作时，检查代码是否一致。如果发现矛盾，把它摆出来：“你的代码会取消整张 Order，但你刚才说可以部分取消。哪个是对的？”

### 就地更新 GLOSSARY.md

一个术语敲定后，立刻就地更新 `GLOSSARY.md`。不要攒起来：发生时就记下。使用 [GLOSSARY-FORMAT.md](./GLOSSARY-FORMAT.md) 中的格式。

`GLOSSARY.md` 应完全不包含实现细节。不要把 `GLOSSARY.md` 当成规格说明、草稿本或存放实现决策的仓库。它就是术语表，仅此而已。

### 谨慎地提议写 ADR

只有以下三条同时成立时，才提议创建 ADR：

1. **难以逆转**：日后改变主意要付出可观的代价
2. **没有上下文会让人意外**：将来的读者会想“他们为什么这么干？”
3. **真实权衡的结果**：当时确实存在其他可行方案，而你出于具体理由选了其中一个

三条里缺任何一条，就跳过 ADR。使用 [ADR-FORMAT.md](./ADR-FORMAT.md) 中的格式。
