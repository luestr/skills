# ADR 格式

ADR 存放在 `docs/adr/` 中，使用连续编号：`0001-slug.md`、`0002-slug.md` 等。

按需创建 `docs/adr/` 目录：只在需要第一条 ADR 时创建。

## 模板

```md
# {决策的简短标题}

{1-3 句话：背景是什么、我们决定了什么、为什么。}
```

就这些。一条 ADR 可以只有一段话。价值在于记录*做过*这个决策以及*为什么*，而不是把各个小节填满。

## 可选小节

只有确实有价值时才包含这些。多数 ADR 用不到。

- **Status** frontmatter（`proposed | accepted | deprecated | superseded by ADR-NNNN`）：在重新审视决策时有用
- **考虑过的方案**：只在被否决的备选方案值得记住时
- **后果**：只在需要点明不明显的下游影响时

## 编号

扫描 `docs/adr/`，找到已有的最大编号，然后加一。

## 何时提议写 ADR

以下三条必须同时成立：

1. **难以逆转**：日后改变主意要付出可观的代价
2. **没有上下文会让人意外**：将来的读者看着代码会想“他们到底为什么这么干？”
3. **真实权衡的结果**：当时确实存在其他可行方案，而你出于具体理由选了其中一个

如果一个决策很容易逆转，就跳过它：你直接逆转就行了。如果它不让人意外，没人会追问为什么。如果当时并不存在真正的备选方案，那除了“我们做了显而易见的事”之外也没什么可记录的。

### 哪些算数

- **架构形态。**“我们采用 monorepo。”“写模型是事件溯源的，读模型投影到 Postgres。”
- **上下文之间的集成模式。**“Ordering 与 Billing 通过领域事件通信，而不是同步 HTTP。”
- **带有锁定效应的技术选型。** 数据库、消息总线、鉴权服务商、部署目标。不是每个库都要记：只是那些换掉要花一个季度的。
- **边界与范围决策。**“客户数据归 Customer 上下文所有；其他上下文只通过 ID 引用它。”明确说“不”和明确说“是”一样有价值。
- **对显而易见路径的有意偏离。**“我们用手写 SQL 而不用 ORM，因为 X。”凡是讲道理的读者会假定相反做法的地方都属于这类。它们能阻止下一位工程师去“修好”本来就有意为之的东西。
- **代码里看不见的约束。**“因为合规要求，我们不能用 AWS。”“因为合作方 API 合约，响应时间必须低于 200ms。”
- **否决理由不明显的被弃方案。** 如果你考虑过 GraphQL，出于微妙的理由选了 REST，就记下来；否则半年后又会有人建议上 GraphQL。
