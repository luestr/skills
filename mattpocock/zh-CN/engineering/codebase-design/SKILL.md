# 代码库设计

设计**深模块（deep module）**：小接口（interface）背后承载大量行为，放在干净的接缝（seam）上，通过该接口就可测试。凡是设计或重构代码的地方，都用这套语言和这些原则。目标是给调用方带来杠杆（leverage），给维护者带来局部性（locality），给所有人带来可测试性。

## 术语表

严格使用这些术语：不要替换成 “component”、“service”、“API” 或 “boundary”。语言一致正是全部意义所在。

**模块（Module）**：任何有接口和实现的东西。刻意不限定尺度：一个函数、类、包，或横跨多层的切片。_Avoid_：unit、component、service。

**接口（Interface）**：调用方要正确使用该模块所必须知道的一切：类型签名，还有不变量、顺序约束、错误模式、必需的配置以及性能特征。_Avoid_：API、signature（太窄，它们只指类型层面的表面）。

**实现（Implementation）**：模块内部的东西，它的代码主体。与**适配器（Adapter）**不同：一个东西可以是小适配器配大实现（一个 Postgres 仓库），也可以是大适配器配小实现（一个内存中的假实现）。当话题是接缝时用 “adapter”，其他情况用 “implementation”。

**深度（Depth）**：接口上的杠杆。调用方（或测试）每学会一单位接口所能施展的行为量。当一个模块的小接口背后承载着大量行为时，它是**深**的；当接口复杂得几乎与实现相当时，它是**浅**的。

**接缝（Seam）** _（Michael Feathers）_：一个你可以在不编辑该处的前提下改变行为的地方；模块接口所在的*位置*。接缝放在哪里本身就是一项设计决策，与接缝后面放什么不同。_Avoid_：boundary（与 DDD 的限界上下文语义过载）。

**适配器（Adapter）**：在接缝上满足某个接口的具体东西。描述的是*角色*（填哪个槽位），不是实质（里面装什么）。

**杠杆（Leverage）**：调用方从深度中得到的东西。每学会一单位接口就能换来更多能力。一份实现回馈 N 个调用点和 M 个测试。

**局部性（Locality）**：维护者从深度中得到的东西。变更、bug、知识和验证集中在一处，而不是散布到各个调用方。修一次，处处都修好。

## 深与浅

**深模块** = 小接口 + 大量实现：

```
┌─────────────────────┐
│       小接口        │  ← 方法少，参数简单
├─────────────────────┤
│                     │
│  实现很深           │  ← 复杂逻辑被隐藏
│                     │
└─────────────────────┘
```

**浅模块（Shallow module）** = 大接口 + 少量实现（避免）：

```
┌─────────────────────────────────┐
│       大接口                    │  ← 方法多，参数复杂
├─────────────────────────────────┤
│  实现很薄                       │  ← 只是透传
└─────────────────────────────────┘
```

设计接口时，问：

- 我能减少方法的数量吗？
- 我能简化参数吗？
- 我能把更多复杂度藏在里面吗？

## 原则

- **深度是接口的属性，不是实现的属性。** 深模块内部可以由小的、可 mock、可替换的部件组成；它们只是不属于接口。一个模块可以有**内部接缝（internal seam）**（对其实现私有，供它自己的测试使用），也可以有接口处的**外部接缝（external seam）**。
- **删除检验（deletion test）。** 想象把这个模块删掉。如果复杂度随之消失，那它只是个透传。如果复杂度在 N 个调用方那里重新出现，那它就在证明自己值得保留。
- **接口就是测试面。** 调用方和测试穿过同一道接缝。如果你想测试接口*之外*的东西，这个模块大概形态不对。
- **一个适配器意味着假想的接缝。两个适配器才意味着真实的接缝。** 除非确实有东西在接缝两侧变化，否则不要引入接缝。

## 为可测试性而设计

好的接口让测试变得自然：

1. **接收依赖，不要自己创建依赖。**

   ```typescript
   // 可测试
   function processOrder(order, paymentGateway) {}

   // 难以测试
   function processOrder(order) {
     const gateway = new StripeGateway();
   }
   ```

2. **返回结果，不要产生副作用。**

   ```typescript
   // 可测试
   function calculateDiscount(cart): Discount {}

   // 难以测试
   function applyDiscount(cart): void {
     cart.total -= discount;
   }
   ```

3. **表面面积小。** 方法越少 = 需要写的测试越少。参数越少 = 测试搭建越简单。

## 关系

- 一个**模块**恰好有一个**接口**（它呈现给调用方和测试的表面）。
- **深度**是**模块**的属性，对照其**接口**来衡量。
- **接缝**是**模块**的**接口**所在之处。
- **适配器**坐在**接缝**上，满足**接口**。
- **深度**为调用方产生**杠杆**，为维护者产生**局部性**。

## 被否决的提法

- **把深度当作实现行数与接口行数之比**（Ousterhout）：这会奖励往实现里注水。我们改用“深度即杠杆”。
- **把“接口”当作 TypeScript 的 `interface` 关键字或类的公开方法**：太窄：这里的接口包含调用方必须知道的所有事实。
- **“边界（boundary）”**：与 DDD 的限界上下文语义过载。说**接缝**或**接口**。
