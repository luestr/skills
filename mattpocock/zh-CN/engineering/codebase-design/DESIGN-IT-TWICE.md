# 设计两遍

当用户想为某个选定的深化候选方案探索备选接口时，用这个并行子 Agent 模式。基于 Ousterhout 的“设计两遍（Design It Twice）”：你的第一个想法不太可能是最好的。

使用 [SKILL.md](SKILL.md) 里的词汇：**模块（Module）**、**接口（Interface）**、**接缝（Seam）**、**适配器（Adapter）**、**杠杆（Leverage）**。

## 流程

### 1. 框定问题空间

启动子 Agent 之前，先针对选定的候选方案写一份面向用户的问题空间说明：

- 任何新接口都必须满足的约束
- 它会依赖哪些依赖，以及它们属于哪个类别（见 [DEEPENING.md](DEEPENING.md)）
- 一段粗略的示例代码草图，用来锚定这些约束——不是方案，只是让约束变得具体

把这份说明给用户看，然后立刻进行第 2 步。用户阅读和思考的同时，子 Agent 并行工作。

### 2. 启动子 Agent

并行启动 3 个以上子 Agent。每个都必须为深化后的模块产出**截然不同**的接口。

用一份独立的技术简报提示每个子 Agent（文件路径、耦合细节、来自 [DEEPENING.md](DEEPENING.md) 的依赖类别、接缝背后是什么）。这份简报独立于第 1 步里面向用户的问题空间说明。给每个 Agent 不同的设计约束：

- Agent 1：“把接口降到最小：最多 1–3 个入口点。最大化每个入口点的杠杆。”
- Agent 2：“最大化灵活性：支持多种用例和扩展。”
- Agent 3：“为最常见的调用方优化：让默认情况毫不费力。”
- Agent 4（如适用）：“围绕端口与适配器设计跨接缝依赖。”

简报里要同时包含 [SKILL.md](SKILL.md) 的词汇和 GLOSSARY.md 的词汇，让每个子 Agent 的命名既与架构语言一致，也与项目的领域语言一致。

每个子 Agent 输出：

1. 接口（类型、方法、参数，外加不变量、顺序、错误模式）
2. 用法示例，展示调用方如何使用它
3. 实现在接缝后面隐藏了什么
4. 依赖策略与适配器（见 [DEEPENING.md](DEEPENING.md)）
5. 权衡：杠杆在哪里高，在哪里薄

### 3. 展示并比较

按顺序展示各个设计，让用户逐个消化，然后用文字比较它们。从**深度（Depth）**（接口上的杠杆）、**局部性（Locality）**（变更集中在哪）和**接缝位置**几个方面对照。

比较之后，给出你自己的推荐：你认为哪个设计最强，为什么。如果不同设计里的元素能很好地结合，就提出一个混合方案。要有主见：用户要的是一个明确的判断，不是一个菜单。
