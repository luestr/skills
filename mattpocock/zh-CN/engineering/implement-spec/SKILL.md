你已拿到一份规格说明。这份规格说明应当带有与之关联的工单，描述如何实现它。

issue 跟踪器应当已经提供给你。如果没有，让用户运行 `/setup-matt-pocock-skills`。

目标是在单个**集成分支**上实现整份规格说明，并按照 issue 跟踪器关闭工作的方式解决每一个工单。

工单不是一串步骤。它们是一张**任务图**，工单之间有阻塞关系。这意味着始终存在一个由已就绪、可抓取工单构成的**前沿**。

与子 Agent 之间的通信应当稀疏。主要通过**上下文指针**沟通：指向规格说明、工单、调研笔记和之前的提交。不要重复指针已经能拿到的信息。

**实现者子 Agent** 应尽可能放到后台运行，以获得最大并发度。

## 步骤

1. 阅读规格说明和工单，理解任务图。

2. （可选）用一个**探索子 Agent** 完成工单要求的任何探索——相关的代码库文件或外部文档。确保探索子 Agent 能保存文件——它应把自己的 markdown 笔记保存在仓库之外的一个目录里，供之后所有子 Agent 访问。这样**实现者子 Agent** 就能专注于实现，而不是探索。

3. 创建集成分支。如果 issue 跟踪器通过 PR 关闭工作，或者用户要求开 PR，就在第 5 步第一次合并之后开一个草稿 PR（一个没有领先 main 的提交的分支开不了 PR），并标记为关闭该规格说明和这些工单。

4. 用**实现者子 Agent** 实现每个工单，每个工单在自己的 worktree、自己的分支上进行。每个实现者子 Agent：
   - 开始前确认自己的 worktree 基于集成分支，如果不是就重置到该分支上；
   - 以 `tdd` 调用 Skill 工具来构建该工单；
   - 在报告完成之前，把集成分支的最新提交合并进自己的分支

5. 一个**实现者子 Agent** 完成后，用**合并子 Agent**把它的工作合并到集成分支。

6. 如果这改变了可做工单的**前沿**，就再启动更多**实现者子 Agent**去处理新工单。这能实现最大并发度。

7. 所有工单完成后，在集成分支上以 `code-review` 调用 Skill 工具。用单个**实现者子 Agent**修复代码评审提出的全部问题。

8. 如果存在草稿 PR，把它标记为可供评审。否则，按照 issue 跟踪器关闭工作的方式解决每一个工单，并报告集成分支。

9. 清理所有**实现者子 Agent** 的 worktree。
