# 改进代码库架构

浮现架构摩擦，提出**深化机会**：把浅模块变成深模块的重构。目标是可测试性与 AI 可导航性。

本命令_依据_项目的领域模型，并建立在一套共享的设计词汇之上：

- 调用 Skill 工具（传入 “codebase-design”）获取架构词汇（**模块**、**接口**、**深度**、**接缝**、**适配器**、**杠杆**、**局部性**）及其原则（删除检验、“接口就是测试面”、“一个适配器 = 假想的接缝，两个 = 真实的接缝”）。每个建议都严格使用这些术语，不要漂移到“组件”“服务”“API”或“边界”。
- `GLOSSARY.md` 里的领域语言为好接缝命名；`docs/adr/` 里的 ADR 记录了本命令不应重新争辩的决策。

## 流程

### 1. 探索

**先定范围，再扫描：YAGNI。**深化一个模块的回报，是让它未来的改动更容易，所以给代码库中最近发生过变化的部分额外加权。看之前先决定*看哪里*：

- 如果用户点名了方向（某个模块、子系统、痛点），就照做，跳过下面的推断。
- 否则，回溯相当长一段提交历史（`git log --oneline`），找出代码库的热点——反复出现的文件和区域——先让这些路径吸引你的注意。如果改动分散、没有明显热点，就把网撒得更大。

先读项目的领域术语表（`GLOSSARY.md`），以及你要触碰区域里的所有 ADR。

然后派出一个子 Agent 走查代码库。不要套用刻板的启发式规则；有机地探索，并记下你体验到摩擦的地方：

- 哪里理解一个概念需要在许多小模块之间来回跳转？
- 哪里模块**浅**，接口几乎和实现一样复杂？
- 哪里为了可测试性抽出了纯函数，但真正的 bug 藏在它们的调用方式里（没有**局部性**）？
- 哪里紧耦合的模块越过接缝泄漏？
- 代码库的哪些部分没有测试，或难以通过当前接口测试？

对你怀疑是浅的所有东西应用**删除检验**：删除它会浓缩复杂度，还是只是把它挪个位置？你要找的信号是“是的，会浓缩”。

### 2. 以 HTML 报告呈现候选方案

把自包含的 HTML 文件写到操作系统临时目录，这样仓库里不会落下任何东西。临时目录优先取 `$TMPDIR`，回退到 `/tmp`（Windows 上为 `%TEMP%`），写入 `<tmpdir>/architecture-review-<timestamp>.html`，让每次运行都有一个新文件。为用户打开它（Linux 用 `xdg-open <path>`，macOS 用 `open <path>`，Windows 用 `start <path>`），并告诉他们绝对路径。

报告用 **CDN 引入的 Tailwind** 做布局和样式，用 **CDN 引入的 Mermaid** 画图——当图形/流程/时序能可靠传达结构时。把 Mermaid 与手工打造的 CSS/SVG 视觉混用：关系呈图形状时（调用图、依赖、时序）用 Mermaid，想要更偏编辑风格的效果时（体量图、横截面、折叠动画）用手工搭建的 div/SVG。每个候选方案都配一幅**前/后对比可视化**。要有视觉表现力。

每个候选方案渲染一张卡片，包含：

- **文件**：涉及哪些文件/模块
- **问题**：当前架构为何造成摩擦
- **方案**：用平实的语言描述将会改变什么
- **收益**：用局部性和杠杆来解释，以及测试将如何改善
- **前 / 后对比图**：并排、手工绘制，展示其浅薄与深化
- **推荐强度**：`Strong`、`Worth exploring`、`Speculative` 之一，渲染成徽章

报告以**首要推荐**小节收尾：你会先处理哪个候选方案，为什么。

**领域词汇用 GLOSSARY.md，架构词汇用 `/codebase-design`。**如果 `GLOSSARY.md` 定义了 “Order”，就说“Order 接收模块”，不要说 “FooBarHandler”，也不要说“Order 服务”。

**ADR 冲突**：如果某个候选方案与现有 ADR 相抵触，只有当摩擦足够真实、值得重新审视该 ADR 时才提出来。在卡片里清楚标出（例如一个警告提示框：_“与 ADR-0007 相抵触，但值得重新开启，因为……”_）。不要罗列 ADR 禁止的每一个理论上的重构。

完整的 HTML 脚手架、图表模式和样式指引见 [HTML-REPORT.md](HTML-REPORT.md)。

先**不要**提出接口。文件写好后，问用户：“你想深入探索其中哪一个？”

### 3. 拷问循环

用户选定一个候选方案后，调用 Skill 工具（传入 “grilling”），与他们一起走查决策树：约束、依赖、深化后模块的形态、接缝背后是什么、哪些测试能存活下来。

决策成形时，副作用就地发生；调用 Skill 工具（传入 “domain-modeling”），让领域模型在过程中保持最新：

- **用 `GLOSSARY.md` 里没有的概念给深化后的模块命名？**把这个术语加进 `GLOSSARY.md`。文件不存在就按需创建。
- **在对话中把模糊的术语磨精准？**当场更新 `GLOSSARY.md`。
- **用户以一条承重理由拒绝候选方案？**提出写一份 ADR，措辞为：_“要我把这件事记录成 ADR，让未来的架构评审不再重复推荐它吗？”_只有当未来的探索者确实需要这个理由来避免重复建议同一件事时才提出；短暂的理由（“现在不值得做”）和不言自明的理由都跳过。
- **想为深化后的模块探索替代接口？**调用 Skill 工具（传入 “codebase-design”），使用它的 design-it-twice 并行子 Agent 模式。
