用户要求做一次**复盘**。你要针对编程 Agent 的**环境**提出改进建议，以改善未来的运行。

## 步骤

1. 以 `writing-for-agents` 调用 Skill 工具，取得写作风格指南。

2. 阅读用户指定会话的一手资料。这可能意味着要在这台机器上翻查会话日志。如果用户没有指定会话，默认是当前会话。

3. 在以下类别中寻找可改进的候选。

- **导航**：Agent 找到正确文件的难易程度如何？文件之间有没有隐藏依赖？加一个**导航指针**会不会更容易？_适用情形_：会话花了很长时间才找到某条信息。
- **自动化检查**：有没有能抓住 Agent 所犯错误的自动化检查？lint、类型检查、测试、文件系统 linter？先读仓库自己的检查命令（它的 `package.json`/构建工具的 `lint`/`check` 脚本、它的 CI 工作流），这样「已经存在却没接线、或悄悄坏掉」的检查才是要报告的结果，而不是重新发明一遍。一个没有**护栏**的仓库（没有 pre-commit 钩子，也没有跑 lint/类型检查/测试命令的 CI 任务）本身就是一项发现：没有 lint 的仓库是长期错失的机会，而不是中性的默认状态。_适用情形_：Agent 犯了某个自动化检查本可以抓住的错误，或者仓库根本没有护栏。
- **编码标准**：是否该给**评审 Agent** 一条新的规则去执行？有没有现成规则该删除或澄清？先给违规分类：**机械性**违规（固定的语法模式、被禁用的 API、导入形态、文件位置规则）要配一个确定性检查，没有例外：仓库自带 linter 里的自定义规则、新的 pre-commit 钩子，或新的 CI 任务，哪个在该仓库的语言和现有护栏下最便宜就用哪个。默认是造检查，而不是写规则。把 `CODING_STANDARDS.md` 留给真正的**判断问题**（跨文件一致性、“与周边风格一致”，以及任何护栏永远替代不了的东西）。_适用情形_：评审 Agent 漏掉了某个错误。
- **全局 AGENTS.md**：有没有哪些引导指令本该移到编码标准（或自动化检查）里？_适用情形_：AGENTS.md 文件特别大——无论在仓库里，还是在用户的全局范围里。
- **工具经济性**：Agent 有没有发出本可精简的高开销工具调用？有没有哪些自定义工具（CLI、MCP）特别浪费 token？_适用情形_：Agent 发出了高开销的工具调用。
- **无效果指令（no-op）**：找出引导文件里那些不改变 Agent 行为的指令。_适用情形_：引导文件又大又笨重。
- **信息获取**：寻找增加 Agent 信息获取途径的机会。把开发服务器日志 tee 出来，让第三方服务只读访问。_适用情形_：某条关键信息当时对 Agent 不可用。

4. 按严重程度依次把这些候选呈现给用户。

## 参考

### 实现与评审

记住，所有工作都经过两个阶段：实现与评审。实现 Agent 的**上下文压力**最大。它负责探索、写代码和调试失败。

评审 Agent 的上下文压力最小——它拿到的是一个 diff，不需要探索。它通常也不需要写代码或调试。

这意味着编码标准应由评审 Agent 来执行，而不是实现 Agent。

### 文件

在仓库里，你可以访问几个文件：

- `CLAUDE.md`/`AGENTS.md`：这些文件会被推送到任何在此仓库工作的 Agent 的上下文窗口。用它们要极其克制，通常只放指向其他文件的**导航指针**。
- `CODING_STANDARDS.md`：这个文件在评审时读，不在实现时读。如果标准文件超过 1,000 行，就加指向文档文件夹的**导航指针**。
- 文档：把文档当作参考文件，由其他文件指向它们。写新文档之前先找找已有的。
- 技能：用技能承载文档（因为技能的 description 会进入 Agent 的上下文窗口），或承载用户手动调用的命令。遵循 `writing-for-agents` 技能中的建议。
