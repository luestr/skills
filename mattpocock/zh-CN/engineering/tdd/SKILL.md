# 测试驱动开发

TDD 就是红 → 绿回路。本技能是一份参考，让这个回路产出值得留下的测试：好测试是什么样、测试放在哪里、有哪些反模式，以及回路的规则。每一节都适用于每一轮循环：在回路之前和之中查阅它们，而不是之后。

探索代码库时，读 `GLOSSARY.md`（如果存在），让测试命名和接口词汇与项目的领域语言一致，并尊重你正在触碰的那片区域的 ADR。

## 什么是好测试

测试通过公共接口验证行为，而不是验证实现细节。代码可以彻底改变；测试不应该。好测试读起来像一份规格说明：“user can checkout with valid cart” 明确告诉你存在什么能力，而且它不关心内部结构，所以能在重构中存活。

示例见 [tests.md](tests.md)，mock 处理准则见 [mocking.md](mocking.md)。

## 接缝：测试放在哪里

**接缝**是你测试所在的公共边界：一个能让你在不伸手进去的情况下观察行为的接口。测试存在于接缝上，绝不针对内部实现。

**只在事先商定的接缝上写测试。** 写任何测试之前，写下要测试的接缝并与用户确认。不在未确认的接缝上写测试。你不可能测试一切，所以事先商定接缝，才能把测试精力花在关键路径和复杂逻辑上，而不是每个边界情况上。

要问：“公共接口是什么，我们应该测试哪些接缝？”为每个提议的接缝写一行说明，讲清它能捕捉什么、漏掉什么。

当接口的形态本身存在疑问时（模块有多深、接缝该落在哪里、接口应该暴露什么），以“codebase-design”调用 Skill 工具来获取这套词汇。它是模块、接口、深度、接缝、适配器、杠杆和局部性这些术语的共同来源，是供查阅的参考，而不是要跑起来的一次会话。

## 反模式

- **与实现耦合**：mock 内部协作者、测试私有方法，或通过侧信道验证（查数据库而不是用接口）。识别标志：重构时测试就断，但行为并没有变。
- **同义反复**：断言用与代码相同的方式重新算出期望值（`expect(add(a, b)).toBe(a + b)`、用同样方式手工推导出的快照、把常量断言为等于它自己），于是它按构造必然通过，永远不可能与代码不一致。期望值必须来自独立的事实来源：一个已知正确的字面量、一个算好的示例，或规格说明。
- **横向切片**：先把所有测试写完，再写所有实现。批量测试验证的是*想象中*的行为：你测的是事物的*形态*，而不是面向用户的行为，测试对真实变化变得不敏感，而且你在理解实现之前就先锁定了测试结构。改为按**垂直切片**工作：一个测试 → 一段实现 → 重复，每个测试都是一颗**曳光弹**，回应上一轮循环教给你的东西。

## 回路的规则

- **先红后绿。** 先写失败的测试，然后只写刚好能让它通过的最少代码。不要预判未来的测试，也不要加投机性的功能。
- **一次一个切片。** 每轮循环：一个接缝、一个测试、一段最小实现。
- **重构不属于这个回路。** 它属于评审阶段（见 `code-review` 技能），而不是红 → 绿这段实现循环。
