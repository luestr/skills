# 问 Matt

你不记得每一个技能，所以要问。

在说明某个技能做什么、或建议跳过某一步之前，先读该技能的 SKILL.md：这里的摘要只用来帮你定位。

**流程**（flow）是穿过各项技能的一条路径。大多数路径沿着一条**主流程**走，有两条**入口匝道**（on-ramp）汇入其中。其余的一切要么独立使用，要么是运行在底层的词汇层。

## 主流程：想法 → 上线

大多数工作都走这条路线。你有一个想法，想把它做出来。

1. **`/grill-with-docs`** 通过访谈把想法打磨得更锋利。只要你**在某个工作目录里工作**，就从这里开始：它有状态，会把学到的东西保留在 `GLOSSARY.md` 和 ADR 里。（没有工作目录？改用 `/grill-me`，见「独立使用」一节。两者运行同一个 `/grilling` 原语；`grill-with-docs` 会留下书面记录，所以只要有仓库可以留下记录，它就是两者中更好的那个。）
2. **分支：每个问题都能在对话里敲定吗？** 如果某个问题需要一个能跑起来的答案（状态、业务逻辑、你必须亲眼看到的 UI），就绕道原型，用 **`/handoff`** 在两个方向搭桥（原型有自己的目录，这正是 `/handoff` 的用途所在；见「阶段边界」）：
   - **`/handoff`** 出去，然后针对那个文件开一个新会话，
   - 用 **`/prototype`** 以一次性（用完即弃）代码回答那个问题，
   - 再 **`/handoff`** 回你学到的东西，并从最初的讨论串里引用它。
3. **分支：这是需要跨多个会话的构建吗？**
   - **是** → **`/to-spec`**（把讨论串变成规格说明），然后 **`/to-tickets`** 把它拆成曳光弹工单，每个工单声明自己的**阻塞关系**。接着按两种方式之一处理工单：
     - 每个工单跑一次 **`/implement`**，**在每次之间用 `/clear` 清空上下文**。在本地跟踪器上，这是 `.scratch/<feature>/issues/` 下每个工单一个文件，由你手动按阻塞项优先的顺序处理；在真实跟踪器上，阻塞关系变成原生的阻塞链接，所以任何阻塞项已完成的工单都可以抓取。每个工单都是自包含的，所以最后一个工单的上下文用完即可丢弃。
     - **`/implement-spec`** 一次运行完成整份规格说明。它把工单读作**任务图**，在已就绪的**前沿**上并行运行实现者子 Agent，并把所有内容落到一个**集成分支**上。当你宁愿编排整个构建、也不愿自己逐张驱动工单时，用它。
   - **否** → 就在原地、同一个上下文窗口里跑 **`/implement`**。

   无论走哪条路，代码都靠驱动 **`/tdd`**（一次一个红-绿切片）来构建，并以 **`/code-review`** 收尾——对 diff 做双轴评审（标准（Standards）+ 规格（Spec））。`/implement` 每个工单都跑这两项；`/implement-spec` 的每个实现者各自驱动 `/tdd`，最后它在集成分支上跑一次 `/code-review`。当你只想在没有完整规格说明的情况下、测试先行地构建一个具体行为时，单独用 **`/tdd`**；当你想针对某个固定基点评审分支或 PR 时，单独用 **`/code-review`**。

   当工作以 PR 的形式提交时，**`/pr`** 塑造它的正文：能展示该改动的最小可视化、证明它有效的改前/改后证据，以及单向门还是双向门的判断。它是模型自动调用的，所以 Agent 每次写 PR 时都会用到它。

4. **`/retro`** 闭环收尾。一次构建之后，尤其是跑偏的那种，它回顾整个会话，建议修改 Agent 的**环境**，而不是代码：导航指针、自动化检查、`/code-review` 执行的编码标准、引导文件、工具链。机械性错误变成确定性检查；需要判断的地方变成编码标准。下一次构建就从更好的环境开始。

### 上下文卫生

让步骤 1–3 待在**同一个不间断的上下文窗口**里（在 `/to-tickets` 之前不要压缩或清空），让拷问、规格说明和工单都建立在同一套思考上。之后每一次 `/implement` 都从工单出发，全新开始。`/retro` 要在它所回顾的那个会话里、清空之前跑；如果已经清空，就让它指向那个会话的日志。

这件事的上限是 **[smart zone](https://www.aihero.dev/ai-coding-dictionary/smart-zone)**：模型仍能犀利推理的那个窗口（在最先进的模型上约 150k tokens）。如果某个会话在 `/to-tickets` 之前逼近这个上限，不要在下滑的状态下硬撑；在最接近的阶段边界处 `/compact`，然后继续（见「阶段边界」）。

## 入口匝道

一种起点情境：它生成工作，然后汇入主流程。

- **bug 和请求越积越多** → **`/triage`**。它让 issue 依次经过分诊角色，产出可直接交给 Agent 的 issue，之后由 **`/implement`** 接手。

  分诊只针对**不是你创建的** issue：bug 报告、外部进来的功能请求，以及任何原始到达的内容。`/to-tickets` 产出的工单已经可直接交给 Agent，所以**不要对它们做分诊**。

- **有东西坏了** → **`/diagnosing-bugs`**。给难缠的那些用：一眼看不透的 bug、时有时无的偶发故障、潜藏在两个已知良好状态之间的回归。在拿到**紧凑的反馈回路**（一条已经会因*这个* bug 变红的命令）之前，它拒绝空谈理论；拿到之后用回归测试修复。修复落地后，在同一个会话里跑 **`/retro`**，问一问什么本可以防止这个 bug；如果真正的发现是没有好的接缝把它锁住，那就是 **`/improve-codebase-architecture`** 的活儿。

- **一项巨大而迷蒙的工程：绿地项目或大型功能构建，大到一个会话装不下** → **`/wayfinder`**，这里认知要求最高的流程。当从这里到目的地的路还看不见时，它在 issue 跟踪器上绘制一张由**决策工单**构成的**共享地图**，一次解决一个，产出**决策，而非交付物**，直到迷雾被推开、道路清晰。**`/grill-with-docs`** 打磨的是你能在一个会话里装下的想法，wayfinder 面向的是装不下的那种；它更慢、更密，所以只留给这种情形，绝不用于范围明确的功能。

  地图清晰之后，**它只交接，不构建**：在 **`/to-spec`** 处汇入主流程——它把地图里相互关联的决策压成一份可构建的计划——然后照常走 `/to-tickets` 和 `/implement`。把地图直接接到 `/implement` 会跳过这次压缩，把关联细节全部丢掉；所以只有当这项工程最终被证明确实很小，才直接去 `/implement`。

## 代码库健康

不是功能开发，只是日常维护。

- **`/improve-codebase-architecture`** 在你得空、想让代码库保持适合 Agent 在其中工作的状态时，随时可以跑。它会浮现**深化机会**；挑一个，就_生成一个想法_，你可以把它带进主流程的 `/grill-with-docs`。它是找出候选方案的勘察；**`/codebase-design`**（见下）则是你为选中者做设计的工作台。

## 底层词汇

两个模型自动调用的参考，运行在其他技能*之下*，各自是自己那套词汇的单一事实来源。当问题出在**词**而不是流程上时，直接找它们；或者让上面的技能把它们带进来。

- **`/domain-modeling`**：打磨项目的*领域*语言：质疑模糊的术语，解决一词多义（“account” 身兼三职），把难以撤销的决策记为 ADR。它是 `/grill-with-docs` 驱动的那门主动纪律，让 `GLOSSARY.md` 保持为一本干净的术语表。
- **`/codebase-design`** 是深模块词汇（模块、接口、深度、接缝、适配器、杠杆、局部性），用来设计模块的*形态*：在干净的接缝处，用小接口承载大量行为。`/tdd` 和 `/improve-codebase-architecture` 都说这套语言。

## 阶段边界

**阶段**是会话内的一块工作：拷问、实现、QA。在两个阶段之间的**边界**上你有五个选项，在它们之间做选择是整张地图里最模糊的决策：

- **继续**：原地不动。不付成本，不丢东西。
- **`/clear`**：清空窗口——当这里的任何东西对接下来都无关紧要时。
- **`/handoff`** 写一个可携带的 markdown 文件。适用面窄：只用于**新的 harness**、**新目录**、**同事**，或在**阶段中途**分叉一项支线任务。它换来的是可携带性。
- **子 Agent**：把范围紧凑的任务送到它自己的窗口，再拿回一份报告。
- **`/compact`** 压缩这份上下文，并用它播种一个新会话。它是**默认选项**，位于决策树的底部，而不是第一顺位。

阅读 [PHASE-BOUNDARIES.md](PHASE-BOUNDARIES.md) 了解有序的决策树：五个问题、每个分支背后的推理，以及为什么一手资料的成本使**继续**成为第一个要判定的选项。决策要在边界**上**做；阶段中途，要么继续，要么把剩余工作拆进子 Agent。

## 独立使用

完全不在主流程上。

- **`/grill-me`**：与 `/grill-with-docs` 同样不留情面的访谈，但**无状态**：不在本地保存任何东西，也不生成 `GLOSSARY.md`。当你**不在工作目录里工作**时用它（打磨一份计划、一个设计、一篇文字，任何底下没有仓库的东西）。如果你在工作目录里，就改用 `/grill-with-docs`：它跑同样的访谈并留下书面记录，所以严格来说它是更好的那个。
- **`/grilling`** 就是访谈这个原语本身：轮次、前沿；事实由 Agent 查，决策由你定。`/grill-me` 和 `/grill-with-docs` 是两个有名字的入口，`/triage`、`/wayfinder` 和 `/improve-codebase-architecture` 都在内部运行它。只有当你想要没有任何包装的访谈时，才直接用它。
- **`/prototype`** 是一个小型的一次性程序，回答一个设计问题：这个状态模型感觉对不对，或者这个 UI 该长什么样。一次性是对代码写法的约束，不是要销毁它的承诺：答案折叠进真实代码，原型本身则从 main 开出一条 `prototype/<name>` 分支保存为**一手资料**，由实现用的 issue 指向它。它是主流程第 2 步里的绕道，但只要设计问题在纸面上难以敲定，随时可以用它。
- **`/research`**：把阅读的功课交给**后台 Agent**：它针对**一手资料**调查一个问题，然后在仓库里留下一份带引用的 Markdown 文件。它阅读时你继续干活。它产出的文件要在 `/grill-with-docs` 处带*入*主流程，因为调研是给思考供料，而不是替代思考。
- **`/to-questionnaire`** 在你卡住的原因既不在你脑子里、也不在代码库里，而在**别人的脑子里**时登场；它写一份问卷让对方填写。它是 `/grill-me` 的反面：不访谈你关于主题的内容，而是访谈你关于**这次发送**（发给谁、你需要拿回什么）的信息，再把问题对准那个缺口。拿回的东西就是 `/grill-with-docs` 或 `/to-spec` 的素材。
- **`/wizard`** 面向只有**人类**才能做的步骤：开通基础设施、设置凭据或 CI secret、在陌生的第三方控制台里一步步点击、执行一次性的迁移或上线切换。它生成一个交互式 bash 脚本，逐个打开 URL、采集每个值，并写入 `.env` 和 GitHub secrets，这样这套流程就不再是你每次都要向 Agent 重新解释的东西。它是模型自动调用的，所以 Agent 一撞上只有你能翻过的墙就会用它。如果 Agent 自己就能做，它就该自己做；这个技能用于人类确实必须参与的场合。
- **`/wait-what`** 是对没听懂的消息的纠正。在对话中途、在任何其他技能内部都能用；Agent 会把你缺的上下文补上，用大白话和 `GLOSSARY.md` 的词汇，把它刚说过的话重新讲一遍。它是事后补救；`/grill-with-docs` 是事前的解药，因为早早商定的共同语言才能让黑话根本不出现。
- **`/teach`**：跨多个会话学习一个概念，把当前目录当作有状态的工作区。
- **`/writing-for-agents`** 是撰写 Agent 消费的文档的参考：技能、AGENTS.md、被指向的文档。

## 前置条件

**`/setup-matt-pocock-skills`**：在第一次工程流程之前运行，配置好其他技能所假定的 issue 跟踪器、分诊标签和文档布局。自定义 issue 跟踪器也可以。
