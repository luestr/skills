# 范围之外知识库

仓库中的 `.out-of-scope/` 目录保存被拒绝功能请求的持久记录。它有两个用途：

1. **组织记忆**：记录某个功能为什么被拒绝，这样 issue 关闭后理由不会丢失
2. **去重**：当新收到的 issue 与此前的拒绝匹配时，技能可以呈现之前的决策，而不是重新争论一遍

## 目录结构

```
.out-of-scope/
├── dark-mode.md
├── plugin-system.md
└── graphql-api.md
```

每个**概念**一个文件，而不是每个 issue 一个文件。请求同一件事的多个 issue 归入同一个文件。

## 文件格式

文件应采用轻松、易读的风格，更像一篇简短的设计文档，而不是数据库条目。用段落、代码示例和例子让理由清晰，并使初次接触它的人也能看懂。

```markdown
# 深色模式

本项目不支持深色模式，也不支持面向用户的主题定制。

## 为什么这属于范围之外

渲染管线假定使用 `ThemeConfig` 中定义的单一配色方案。
支持多主题将需要：

- 一个包裹整棵组件树的主题上下文提供者
- 按组件解析主题感知的样式
- 一个保存用户主题偏好的持久化层

这是一项重大的架构改动，与本项目专注内容创作的定位不符。
主题定制属于下游消费者的问题，他们负责嵌入或再分发产物。

```ts
// 当前的 ThemeConfig 接口并非为运行时切换而设计：
interface ThemeConfig {
  colors: ColorPalette; // 单一配色方案，在构建时解析
  fonts: FontStack;
}
```

## 此前的请求

- #42：“添加深色模式支持”
- #87：“无障碍的夜间主题”
- #134：“深色主题选项”
```

### 命名文件

为概念使用简短、描述性的 kebab-case 名称：`dark-mode.md`、`plugin-system.md`、`graphql-api.md`。名称应足够易辨认，让人浏览目录时不用打开文件就能明白被拒绝的是什么。

### 撰写理由

理由应当有实质内容：不是“我们不想要这个”，而是为什么。好的理由会引用：

- 项目范围或理念（“本项目专注于 X；主题定制是下游的事”）
- 技术约束（“支持这个需要 Y，与我们的 Z 架构冲突”）
- 战略决策（“我们选择用 A 而不是 B，因为……”）

理由应当长期有效。避免引用临时情况（“我们现在太忙了”）；那不是真正的拒绝，而是延后。

## 何时检查 `.out-of-scope/`

在分诊期间（第 1 步：收集上下文），读取 `.out-of-scope/` 中的所有文件。评估新 issue 时：

- 检查请求是否匹配已有的范围之外概念
- 匹配依据是概念相似度，而不是关键词：“night theme”与 `dark-mode.md` 匹配
- 如果匹配，把它呈现给维护者：“这与 `.out-of-scope/dark-mode.md` 相似。我们之前拒绝过它，理由是 [reason]。你的想法还是这样吗？”

维护者可能：

- **确认**：新 issue 被加入现有文件的“此前的请求”列表，然后关闭
- **重新考虑**：范围之外文件被删除或更新，issue 继续走正常分诊流程
- **不同意**：这些 issue 相关但不同，继续走正常分诊流程

## 何时写入 `.out-of-scope/`

仅当**enhancement**（而非 bug）被当作 `wontfix` *拒绝*时。这同样适用于 enhancement PR：被拒绝的 PR 也记录在这里，避免同一个请求又以新代码的形式回来。

当某个东西因**已经实现**而被关闭为 `wontfix` 时，**不要**写到这里。那是已构建的功能，不是被拒绝的功能；记录它会让去重检查被虚假的拒绝污染。这种情况应改为在关闭评论中指明该功能已存在的位置。

流程：

1. 维护者判定某个功能请求属于范围之外
2. 检查是否已存在匹配的 `.out-of-scope/` 文件
3. 如果有：把新 issue 追加到“此前的请求”列表
4. 如果没有：用概念名称、决策、理由和第一条此前请求创建新文件
5. 在 issue 上发布评论，解释该决定并提及 `.out-of-scope/` 文件
6. 用 `wontfix` 标签关闭该 issue

## 更新或删除范围之外文件

如果维护者对之前拒绝的概念改变了主意：

- 删除 `.out-of-scope/` 文件
- 技能不需要重新打开旧的 issue；它们是历史记录
- 触发重新考虑的新 issue 继续走正常分诊流程
