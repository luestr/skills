# 撰写 Agent 简报

Agent 简报是 issue 或 PR 移到 `ready-for-agent` 时，发布在 GitHub issue 或 PR 上的一条结构化评论。它是 AFK Agent 据以工作的权威规格说明。原始正文和讨论是上下文：Agent 简报才是契约。

简报说明**Agent 应该做什么**，这一点延伸到两种情形：对 issue，是从零构建这个改动；对 PR，则是对*现有 diff* 还需要做什么：完成它、补齐缺口、处理评审意见。两种情形原则相同；下面的 PR 示例展示了其中的差异。

## 原则

### 耐久性优先于精确性

该 issue 可能会在 `ready-for-agent` 上停留数天或数周。在此期间代码库会发生变化。写简报时要让它在文件被重命名、移动或重构后依然有用。

- **要**描述接口、类型和行为契约
- **要**点名 Agent 应该查找或修改的具体类型、函数签名或配置形态
- **不要**引用文件路径：它们会过期
- **不要**引用行号
- **不要**假设当前的实现结构会保持不变

### 描述行为，而非过程

描述系统应该做**什么**，而不是**如何**实现。Agent 会重新探索代码库，自己做实现决策。

- **好：**“`SkillConfig` 类型应接受一个可选的 `schedule` 字段，类型为 `CronExpression`”
- **差：**“打开 src/types/skill.ts，在第 42 行加一个 schedule 字段”
- **好：**“当用户不带参数运行 `/triage` 时，应看到需要关注的 issue 摘要”
- **差：**“在主处理函数里加一个 switch 语句”

### 完整的验收标准

Agent 需要知道什么时候算完成。每份 Agent 简报都必须有具体、可测试的验收标准。每条标准都应可独立验证。

- **好：**“运行 `gh issue list --label needs-triage` 会返回已通过初步分类的 issue”
- **差：**“分诊应该能正常工作”

### 明确的范围边界

说明哪些内容在范围之外。这能防止 Agent 镀金（gold-plating），或对相邻功能做假设。

## 模板

```markdown
## Agent 简报

**分类：** bug / enhancement
**摘要：** 用一行说明需要发生什么

**当前行为：**
描述现在会发生什么。对 bug，这是坏掉的行为。
对 enhancement，这是该功能所基于的现状。

**期望行为：**
描述 Agent 的工作完成之后应该发生什么。
要具体说明边界情况和错误条件。

**关键接口：**
- `TypeName`：需要改什么，以及为什么
- `functionName()` 的返回类型：它当前返回什么 vs 应该返回什么
- 配置形态：需要新增的任何配置选项

**验收标准：**
- [ ] 具体、可测试的标准 1
- [ ] 具体、可测试的标准 2
- [ ] 具体、可测试的标准 3

**范围之外：**
- 本 issue 中不应修改或处理的事项
- 看似相关但独立的相邻功能
```

## 示例

### 好的 Agent 简报（bug）

```markdown
## Agent 简报

**分类：** bug
**摘要：** 技能描述截断会截在词中间，产生破损的输出

**当前行为：**
当技能描述超过 1024 个字符时，无论词边界如何，
它都会在正好 1024 个字符处截断。这会产出
以半个词结尾的描述（例如 "Use when the user wants to confi"）。

**期望行为：**
截断应停在 1024 个字符之前的最后一个词边界处，
并追加 "..." 表示发生了截断。

**关键接口：**
- `SkillMetadata` 类型的 `description` 字段：无需改类型，
  但填充它的校验/处理逻辑需要遵守词边界
- 任何读取 SKILL.md frontmatter 并提取 description 的函数

**验收标准：**
- [ ] 少于 1024 字符的描述保持不变
- [ ] 超过 1024 字符的描述在 1024 字符前的最后一个词边界处截断
- [ ] 截断后的描述以 "..." 结尾
- [ ] 包含 "..." 在内的总长度不超过 1024 字符

**范围之外：**
- 修改 1024 字符上限本身
- 支持多行描述
```

### 好的 Agent 简报（enhancement）

```markdown
## Agent 简报

**分类：** enhancement
**摘要：** 添加 `.out-of-scope/` 目录支持，用于记录被拒绝的功能请求

**当前行为：**
当功能请求被拒绝时，issue 会带着 `wontfix` 标签和一条评论被关闭。
决策或理由没有任何持久记录。
将来出现类似请求时，维护者只能回忆或搜索当时的讨论。

**期望行为：**
被拒绝的功能请求应记录在 `.out-of-scope/<concept>.md` 文件中，
文件中包含决策、理由，以及所有曾请求该功能的 issue 的链接。
分诊新 issue 时，应检查这些文件是否存在匹配。

**关键接口：**
- `.out-of-scope/` 中的 Markdown 文件格式：每个文件应有
  `# 概念名称` 标题、`**决策：**` 行、`**理由：**` 行，
  以及带 issue 链接的 `**此前的请求：**` 列表
- 分诊流程应尽早读取所有 `.out-of-scope/*.md` 文件，
  并按概念相似度把新收到的 issue 与它们匹配

**验收标准：**
- [ ] 把某个功能作为 wontfix 关闭时，会在 `.out-of-scope/` 中创建/更新文件
- [ ] 该文件包含决策、理由，以及指向被关闭 issue 的链接
- [ ] 如果已存在匹配的 `.out-of-scope/` 文件，就把新 issue 追加到其“此前的请求”列表，而不是创建重复文件
- [ ] 分诊期间，当新 issue 与此前被拒绝的请求匹配时，会检查并呈现现有的 `.out-of-scope/` 文件

**范围之外：**
- 自动匹配（由人确认匹配结果）
- 重新开启此前被拒绝的功能
- bug 报告（只有被拒绝的 enhancement 才写入 `.out-of-scope/`）
```

### 好的 Agent 简报（PR）

对于 PR，“当前行为”描述 diff 的状态，简报要求 Agent 完成或修复它，而不是从零构建。

```markdown
## Agent 简报

**分类：** enhancement
**摘要：** 完成贡献者为 `triage list` 添加的 `--json` 输出标志

**当前行为：**
该 PR 添加了一个把 issue 列表序列化为 JSON 的 `--json` 标志。正常
路径可用，diff 也符合项目的命令结构。还剩两处缺口：错误仍以人类
可读文本（而非 JSON）打印，且新标志没有测试覆盖。

**期望行为：**
使用 `--json` 时，所有输出（包括错误）都是 stdout 上格式良好的 JSON，
命令的退出码保持不变。不加该标志时，现有的人类可读输出不受影响。

**关键接口：**
- 命令的错误路径在 `--json` 下应输出 `{ "error": string }`，
  而不是纯文本错误
- 复用该 PR 已经添加的现有序列化器；不要再引入第二个

**验收标准：**
- [ ] `triage list --json` 在成功和错误两种情况下都输出合法 JSON
- [ ] 退出码与非 JSON 命令一致
- [ ] 有测试覆盖 `--json` 的成功输出和一个错误场景
- [ ] 默认（非 JSON）输出逐字节保持不变

**范围之外：**
- 为任何其他命令添加 `--json`
- 修改该 PR 已定义的成功载荷的 JSON 形态
```

### 差的 Agent 简报

```markdown
## Agent 简报

**摘要：** 修复分诊的 bug

**要做什么：**
分诊那东西坏了。看看主文件，把它修好。
大概第 150 行附近的那个函数有问题。

**要改的文件：**
- src/triage/handler.ts（第 150 行）
- src/types.ts（第 42 行）
```

这个简报差在：
- 没有分类
- 描述含糊（“分诊那东西坏了”）
- 引用了会过期的文件路径和行号
- 没有验收标准
- 没有范围边界
- 没有描述当前行为与期望行为
