# 分诊

让项目 issue 跟踪器上的 issue 在一个小型的分诊角色状态机中流转。

如果本仓库把外部 pull request 当作一种请求入口（见 issue 跟踪器配置），分诊也覆盖它们：**PR 就是附带代码的 issue**，使用相同的角色、相同的状态和相同的状态机，只有几处差异在下文标为“针对 PR”。按照跟踪器配置把单独出现的 `#42` 解析为 issue 或 PR。

分诊期间发布到 issue 跟踪器的每条评论或 issue **必须**以这段免责声明开头：

```
> *本内容由 AI 在分诊过程中生成。*
```

## 参考文档

- [AGENT-BRIEF.md](AGENT-BRIEF.md)：如何撰写耐久的 Agent 简报
- [OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)：`.out-of-scope/` 知识库如何运作

## 角色

两个**分类**角色：

- `bug`：有东西坏了
- `enhancement`：新功能或改进

五个**状态**角色：

- `needs-triage`：维护者需要评估
- `needs-info`：等待报告者提供更多信息
- `ready-for-agent`：已完整明确，可供 AFK Agent 直接上手
- `ready-for-human`：需要人类实现
- `wontfix`：不会处理

对于 PR，同样的状态是针对所附代码而言的：`ready-for-agent` 表示已附上简报，Agent 应在该 diff 上推进下一步；`ready-for-human` 表示已可由人类合并。

每个已分诊的 issue 都应恰好带有一个分类角色和一个状态角色。如果状态角色相互冲突，先标记出来并询问维护者，再做其他任何事。

这些是规范的角色名。issue 跟踪器中实际使用的标签字符串可能不同。映射关系应该已经提供给你。如果没有，让用户运行 `/setup-matt-pocock-skills`。

状态流转：未打标签的 issue 通常先进入 `needs-triage`；从那里再转到 `needs-info`、`ready-for-agent`、`ready-for-human` 或 `wontfix`。报告者回复后，`needs-info` 返回 `needs-triage`。维护者随时可以覆盖这些流转；遇到看起来异常的流转要标记出来，并在继续之前先询问。

## 调用

维护者调用 `/triage`，用自然语言描述他们的诉求。理解请求并执行。示例：

- “把需要我关注的东西列出来”
- “我们看看 #42”（issue 或 PR）
- “把 #42 移到 ready-for-agent”
- “有什么已经可供 Agent 接手了？”

## 展示需要关注的内容

查询 issue 跟踪器，按三个分组呈现，最早的在前：

1. **未打标签**：从未分诊过。
2. **`needs-triage`**：评估进行中。
3. **`needs-info` 且自上次分诊记录以来报告者有活动**：需要重新评估。

当 PR 在范围内时，这些分组也要包含外部 PR，并在每行标注 `[PR]` 或 `[issue]`。发现环节只呈现*外部* PR（跟踪器配置定义谁算外部），因此协作者正在处理中的 PR 不属于分诊工作。这个过滤仅用于发现；明确点名的 PR 无论作者是谁都要分诊。

显示数量，并为每一项给出一行摘要。让维护者挑选。

## 分诊特定的 issue 或 PR

1. **收集上下文。** 完整阅读该 issue 或 PR（正文、评论、标签、作者、日期；如果是 PR，还要看 diff）。解析之前的任何分诊记录，避免重复询问已解决的问题。使用项目的领域术语表探索代码库，并遵守该区域的 ADR。对代码库运行两项检查：(a) **冗余**：按领域概念（而不只是请求的措辞）搜索所请求行为的已有实现，并报告你查找过的地方。如果找到，它就是“已实现”的 `wontfix`（第 5 步）。(b) **此前拒绝**：读取 `.out-of-scope/*.md`，找出与本次请求相似的文件并呈现。

2. **给出建议。** 告诉维护者你推荐的分类和状态及理由，并附上与该请求相关的简要代码库概况（包括它是否已经实现）。等待指示。

3. **验证说法。** 在任何拷问之前，先确认说法站得住脚。对于 bug，按报告者给出的步骤复现。对于 PR，确认 diff 确实做了它声称的事：检出代码，运行相关测试或命令。报告结果：已确认（附代码路径）、失败，还是细节不足（强烈的 `needs-info` 信号）。验证得到确认，会让 Agent 简报强得多。

4. **拷问（如需要）。** 如果请求需要细化，调用 Skill 工具两次，分别加载 “grilling” 和 “domain-modeling”，一轮问题一轮问题地把它拷问成型，同时打磨领域术语，并在决策敲定时顺手更新 `GLOSSARY.md`/ADR。

5. **落实结果：**
   - `ready-for-agent`：发布一条 Agent 简报评论（[AGENT-BRIEF.md](AGENT-BRIEF.md)）。
   - `ready-for-human`：与 Agent 简报结构相同，但要说明为什么不能委派给 Agent（需要判断权衡、外部访问、设计决策、人工测试）。
   - `needs-info`：发布分诊记录（模板见下）。
   - 对于 `wontfix`，关闭该 issue，评论内容取决于*原因*：
     - **已实现**：该改动已存在于代码库中。指出它所在的位置；**不要**写入 `.out-of-scope/`（那个知识库用于*被拒绝*的请求，而不是已构建的请求）。
     - **被拒绝（bug）**：礼貌地解释，然后关闭。
     - **被拒绝（enhancement）**：写入 `.out-of-scope/`，在评论中链接到该文件，然后关闭（[OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)）。
   - `needs-triage`：应用该角色。如果有部分进展，可选地留一条评论。

## 快速覆盖状态

如果维护者说“把 #42 移到 ready-for-agent”，就相信他们，直接应用该角色。确认你将要做什么（角色变更、评论、关闭），然后执行。跳过拷问。如果在没有拷问式访谈的情况下移到 `ready-for-agent`，询问他们是否要写 Agent 简报。

## Needs-info 模板

```markdown
## 分诊记录

**目前已确认的内容：**

- 要点 1
- 要点 2

**还需要你（@reporter）提供：**

- 问题 1
- 问题 2
```

把拷问期间解决的所有内容都记到“目前已确认的内容”之下，这样工作成果不会丢失。问题必须具体、可执行，而不是“请提供更多信息”。

## 恢复之前的会话

如果该 issue 或 PR 上存在之前的分诊记录，先阅读它们，检查报告者是否已回答了任何悬而未决的问题，并在继续之前呈现更新的全貌。不要重复询问已解决的问题。
