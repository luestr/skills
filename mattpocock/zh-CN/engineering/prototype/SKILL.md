# 原型

原型是**回答某个问题的一次性代码**。问题决定它的形态。

## 选一条分支

用用户的提示词、周围的代码，或者在用户就在旁边时直接问，判断正在回答的是哪个问题：

- **“这套逻辑／状态模型感觉对吗？”** → [LOGIC.md](LOGIC.md)。构建一个可分享的单一 HTML 文件（自由试玩按钮加标签页式引导演练），把状态机推进那些纸上难以推理的场景，并且非开发者也能操作。
- **“这个应该长什么样？”** → [UI.md](UI.md)。在单个路由上生成几个截然不同的 UI 变体，通过 URL 查询参数和悬浮底栏切换。

两条分支产出的东西差别很大，选错会浪费整个原型。如果问题确实含糊、又联系不上用户，就默认选与周围代码更匹配的那条分支（后端模块 → 逻辑；页面或组件 → UI），并在原型顶部说明这一假设。

## 两条分支都适用的规则

1. **从第一天起就是一次性的（用完即弃），并且明确标注。** 把原型代码放在它真正会被使用的位置附近（紧挨着它所针对的模块或页面），让上下文一目了然；但命名要让人随便一看就知道这是原型，不是生产代码。对于一次性的 UI 路由，遵守项目已有的路由约定；不要发明新的顶层结构。
2. **运行起来毫不费力。** UI 原型从项目任务运行器里的一条命令启动：`pnpm <name>`、`python <path>`、`bun <path>` 等。逻辑演示则是用户双击打开的一个 HTML 文件。无论哪种，启动都不需要动脑。
3. **默认不做持久化。** 状态存在内存里。持久化是原型要_检验_的东西，而不是它应当依赖的东西。如果问题明确涉及数据库，就用一个临时 DB，或者用一个名字明确写着 “PROTOTYPE, wipe me” 的本地文件。
4. **跳过打磨。** 不要测试，不要写超出让原型_能跑起来_所必需的错误处理，不要抽象。重点是把东西快速学会。
5. **把状态暴露出来。** 每次操作之后（逻辑）或每次切换变体时（UI），打印或渲染完整的相关状态，让用户看到变了什么。
6. **收尾时把它留存下来。** 把验证过的决策并入真实代码，然后把原型本身作为**一手资料**留存：提交到一个一次性分支上，不要进 main，并在实现 issue 上留一个指向该分支的上下文指针。答案也要留下来（结论以及它敲定的问题），记在 issue 或某次提交里。main 分支只保留验证过的决策。
