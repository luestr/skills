# UI 原型

在单个路由上生成**几个截然不同的 UI 变体**，从悬浮底栏切换。用户在浏览器里来回翻变体，挑一个（或从每个里偷一点），然后把其余的扔掉。

如果问题关乎逻辑／状态而不是某个东西长什么样，那就是走错了分支。用 [LOGIC.md](LOGIC.md)。

## 什么时候该用这个形态

- “这个页面应该长什么样？”
- “我想在定下来之前先看看这个仪表盘的几个方案。”
- “给设置页换个布局试试。”
- 凡是会让用户在脑子里花上一整天比较三个模糊设计稿的场合。

## 两种子形态：强烈偏向子形态 A

当 UI 原型**紧贴着应用其余部分**时，判断起来容易得多：真实的页头、真实的侧边栏、真实的数据、真实的密度。单独一个一次性路由是真空：每个变体孤立看都没问题。只要有一个说得过去的现有页面可以承载这些变体，就默认用子形态 A。只有当原型确实在附近没有落脚处时，才动用子形态 B。

### 子形态 A：对现有页面做调整（首选）

路由已经存在。变体**在同一个路由上**渲染，由 `?variant=` URL 查询参数控制。现有的数据获取、参数和鉴权全部保留，只有渲染被替换。这是默认做法；除非有明确理由不这么做，否则就选它。

如果原型针对的东西还没有页面，但*本来就会自然地嵌在某个页面里*（仪表盘的一个新区块、设置页上的一张新卡片、现有流程里的一个新步骤），它仍然属于子形态 A。把变体挂载进宿主页面。

### 子形态 B：新建页面（最后手段）

只有当被原型化的东西确实没有任何现有页面可容纳时才用它（例如一个全新的顶层界面，或者一个没法嵌进任何合理位置的流程）。

按项目已有的路由约定创建一个**一次性路由**。不要发明新的顶层结构。命名要让人一眼看出是原型（例如在路径或文件名里带上 `prototype` 一词）。同样用 `?variant=` 模式。

在决定用子形态 B 之前，先核对一下：真的没有任何现有页面可以嵌入它吗？空路由会掩盖有内容的页面才会暴露的设计问题。

两种子形态的悬浮底栏完全相同。

## 流程

### 1. 写明问题并选定 N

默认 **3 个变体**。超过 5 个就不再是截然不同，而开始变成噪音，所以上限就卡在这里。

用一行写下计划，放在原型所在位置或文件顶部的注释里：

> “设置页的三个变体，通过 `?variant=` 切换，挂在现有的 `/settings` 路由上。”

无论用户现场是否会提出反对，这都管用。

### 2. 生成截然不同的变体

给每个变体起草。每一个都要满足：

- 页面的用途，以及它能访问到的数据。
- 项目的组件库／样式方案（TailwindCSS、shadcn、MUI、纯 CSS，等等）。
- 一个清晰的导出组件名，例如 `VariantA`、`VariantB`、`VariantC`。

变体必须**结构上不同**：布局不同、信息层级不同、主要可供性不同，而不只是颜色不同。三个稍微调过的卡片网格不是 UI 原型，是壁纸。如果两份草稿出来太像，就带着明确的“不要用卡片网格”指示重做其中一个。

### 3. 把它们接起来

在路由上创建一个切换器组件：

```tsx
// 伪代码，按项目的框架调整
const variant = searchParams.get('variant') ?? 'A';
return (
  <>
    {variant === 'A' && <VariantA {...data} />}
    {variant === 'B' && <VariantB {...data} />}
    {variant === 'C' && <VariantC {...data} />}
    <PrototypeSwitcher variants={['A','B','C']} current={variant} />
  </>
);
```

子形态 A（现有页面）：把所有现有的数据获取保留在切换器之上；每个变体只改变渲染出的子树。

子形态 B（新页面）：`/prototype/<name>` 下的一次性路由挂载同一个切换器。

### 4. 构建悬浮切换器

屏幕底部居中的一个小的固定定位栏，由三部分组成：

- **左箭头**：切到上一个变体（循环）。
- **变体标签**：显示当前变体键，如果变体导出了名称，也显示那个名称。例如 `B (Sidebar layout)`。
- **右箭头**：向前切换（循环）。

行为：

- 点击箭头会更新 URL 查询参数（用框架的路由器，例如 Next 上的 `router.replace`、React Router 上的 `navigate` 等），这样变体可以分享，刷新后也稳定。
- 键盘：`←` 和 `→` 方向键同样可以循环切换。当焦点在 `<input>`、`<textarea>` 或 `[contenteditable]` 上时，不要拦截方向键。
- 在视觉上与页面区分开（例如高对比度的胶囊样式、轻微阴影），让人明显看出它不属于正在评估的设计。
- 在生产构建中隐藏：用 `process.env.NODE_ENV !== 'production'` 或等价的检查做门控，这样混进来的原型合并不会把这条栏发给用户。

把切换器放进单个共享组件，让两种子形态都能复用它。放在项目里共享 UI 所在的位置。

### 5. 交出去

把 URL（以及各个 `?variant=` 键）摆出来。用户有空的时候会自己翻一遍。有价值的反馈通常是**“我想要 B 的页头配 C 的侧边栏”**，那才是他们真正想要的设计。

### 6. 留下答案并清理

一旦某个变体胜出，就记下答案（选了哪个变体、为什么），然后按 [SKILL](SKILL.md) 描述的方式把原型留存下来。把胜出的部分并入真实代码，其余的移到一次性分支，不要移进 main：

- **子形态 A**：把胜出的变体并入现有页面；从 main 上丢掉落选的变体和切换器。
- **子形态 B**：把胜出的变体提升为真实路由；从 main 上丢掉一次性路由和切换器。

整套变体是一手资料，所以它落在一次性分支上，而不是垃圾桶里——留在 main 分支上的变体组件和切换器会很快腐烂，扰得下一个读者一头雾水。

## 反模式

- **只有颜色或文案不同的变体。** 那是微调，不是原型。真正的变体在结构上就有分歧。
- **变体之间共享太多代码。** 共享一个 `<Header>` 没问题；共享一个 `<Layout>` 就背离了初衷。每个变体都应该能自由地抛弃布局。
- **把变体接到真实的数据修改上。** 只读原型没问题。如果某个变体需要修改数据，就让它指向一个桩：问题是“这应该长什么样”，不是“后端能不能用”。
- **把原型直接提升到生产。** 变体代码是在原型约束下写的（没有测试，错误处理最少）。并入的时候好好重写它。
