从两个维度评审 `HEAD` 与用户提供的固定基点之间的 diff：

- **标准（Standards）**：代码是否符合本仓库有文档记录的编码标准？
- **规格（Spec）**：代码是否忠实实现了来源 issue / spec？

两个维度都用**并行子 Agent** 运行，以免互相污染上下文，然后由本技能汇总它们的发现。

issue 跟踪器应当已经提供给你。如果没有，让用户运行 `/setup-matt-pocock-skills`。

## 流程

### 1. 钉住固定基点

用户说的就是固定基点（一个提交 SHA、分支名、标签、`main`、`HEAD~5` 等）。如果用户没有指定，就问。

一次性确定 diff 命令：`git diff <fixed-point>...HEAD`（三个点，所以是与 merge-base 比较）。同时用 `git log <fixed-point>..HEAD --oneline` 记下提交列表。

继续之前，先确认这个固定基点能解析（`git rev-parse <fixed-point>`），并且 diff 非空。无效的 ref 或空 diff 应该在这里失败，而不是在两个并行子 Agent 里面才失败。

### 2. 确定 spec 来源

按以下顺序寻找来源 spec：

1. 提交信息里的 issue 引用（`#123`、`Closes #45`、GitLab `!67` 等），通过跟踪器文档里的工作流获取。
2. 用户作为参数传入的路径。
3. `docs/`、`specs/` 或 `.scratch/` 下与分支名或特性匹配的 spec 文件。
4. 如果什么都没找到，问用户 spec 在哪里。如果用户说没有，**规格**子 Agent 会跳过并报告 “no spec available”。

### 3. 确定标准来源

在仓库里搜索每一个记录“代码该怎么写”的文件。如果存在 `CODING_STANDARDS.md` 或 `CONTRIBUTING.md`，它必须在这份列表上。

除了仓库已有的文档之外，标准维度永远带着下面这套**坏味道基线**：一组固定的 Fowler 代码坏味道（_Refactoring_，第 3 章），即使仓库什么都没写也适用。有两条规则约束它：

- **仓库优先。** 仓库里成文的标准永远胜出；如果它认可了基线本会标记的东西，就压掉那条坏味道。
- **永远只是主观判断。** 每条坏味道都是一个贴了标签的启发式提示（“可能的 Feature Envy”），绝不是硬违规。和这里的所有标准一样，工具已经强制检查的内容一律跳过。

每条坏味道的写法是*它是什么* → *怎么修*；拿它去对照 diff：

- **神秘命名（Mysterious Name）**：函数、变量或类型的名字不能透露它做什么、装什么。→ 重命名；如果想不出一个诚实的名字，说明设计本身含混。
- **重复代码（Duplicated Code）**：同一种逻辑形态在这次变更中出现在不止一个 hunk 或文件里。→ 抽出共有的形态，两处都调用它。
- **依恋情结（Feature Envy）**：一个方法访问别的对象的数据比访问自己的更多。→ 把这个方法挪到它依恋的数据上去。
- **数据泥团（Data Clumps）**：同一小撮字段或参数总是一起出现（一个想要诞生的类型）。→ 把它们打包成一个类型，传那个类型。
- **基本类型偏执（Primitive Obsession）**：用一个原始类型或字符串代表本该有自己的类型的领域概念。→ 给这个概念一个小类型。
- **重复的 switch（Repeated Switches）**：针对同一类型的同一套 `switch`/`if` 级联在整个变更中反复出现。→ 改用多态，或者用两处共享的一张映射表。
- **霰弹式修改（Shotgun Surgery）**：一次逻辑变更迫使你在 diff 里许多文件上散落地做编辑。→ 把一起变化的东西聚到一个模块里。
- **发散式变化（Divergent Change）**：一个文件或模块因为几个不相关的原因被编辑。→ 拆分，让每个模块只因为一个原因而变化。
- **夸夸其谈通用性（Speculative Generality）**：为了 spec 并不存在的需要而添加抽象、参数或钩子。→ 删掉；先内联回去，直到出现真实需要。
- **过长的消息链（Message Chains）**：调用方不该依赖的 `a.b().c().d()` 长链导航。→ 把这段游走藏到第一个对象上的一个方法后面。
- **中间人（Middle Man）**：一个类或函数大部分只是往下委派。→ 砍掉它，直接调用真正的目标。
- **被拒绝的遗赠（Refused Bequest）**：子类或实现者忽略或覆盖了它继承的大部分东西。→ 放弃继承，改用组合。

### 4. 并行启动两个子 Agent

把两个子 Agent 调用一起发出，都在前台运行，然后汇总它们返回的报告。

**标准子 Agent 的提示词**应包含：

- 完整的 diff 命令和提交列表。
- 第 3 步里找到的标准来源文件列表，**加上第 3 步的坏味道基线**，完整粘贴进去（子 Agent 没有别的途径拿到它）。
- 简报：“在相关的文件／hunk 上报告：(a) diff 中每一处违反成文标准的地方：引用该标准（文件 + 规则）；(b) 你发现的任何基线坏味道：说出名字并引用该 hunk。区分硬违规与主观判断：违反成文标准可以是硬违规，但基线坏味道永远只是主观判断，而且仓库里有文档的标准会覆盖基线。跳过任何工具已经强制检查的东西。400 词以内。”

**规格子 Agent 的提示词**应包含：

- diff 命令和提交列表。
- spec 的路径或已获取的内容。
- 简报：“报告：(a) spec 要求但缺失或不完整的需求；(b) diff 里没被要求的行为（范围蔓延）；(c) 看起来实现了、但实现方式看着不对的需求。每条发现都引用对应的 spec 原文行。400 词以内。”

如果 spec 缺失，跳过规格子 Agent，并在最终报告里注明。

### 5. 汇总

把两份报告分别放在 `## 标准` 和 `## 规格` 标题下，原样或稍作清理。**不要**合并或重新排序这些发现，因为两个维度是刻意分开的（见 _为什么分两个维度_）。

最后用一行总结：每个维度的发现总数，以及_每个维度内_最严重的问题（如果有）。不要跨维度挑出唯一的赢家：分离维度正是为了阻止这种重新排序。

## 为什么分两个维度

一项变更可能通过一个维度、在另一个维度上失败：

- 代码遵循了每一条标准，但实现的东西是错的 → **标准通过，规格失败。**
- 代码完全照 issue 的要求做了，但破坏了项目的约定 → **规格通过，标准失败。**

分开报告能防止一个维度掩盖另一个维度。
